# Security model

This page distinguishes controls enforced by current code from gaps found by reading current code. Desired controls belong in active plans, not in the description of current behavior.

## Public boundary

WebHost listens on port 20229, serves the SPA, and proxies `/api/**` to Gateway. Gateway owns application authentication and authorization. WebHost and Gateway default to loopback; configuring either listener on a non-loopback address requires a TLS certificate. WebHost accepts a PKCS#12 edge certificate through `WebHost:Tls:CertificatePath` and `WebHost:Tls:CertificatePassword`.

Browser authentication uses signed short-lived `k1` access tokens with expiry and a server-side generation lookup, plus opaque hashed rotating refresh sessions in SQLite. Gateway applies fallback authentication and explicit anonymous setup/login routes, then enforces owner/admin checks at resource endpoints. User-owned agents and sessions remain owner-scoped even for ordinary administrative UI operations.

Google and Microsoft sign-in is offered only when the connector-auth host is a real HTTPS origin and that provider's public client id is configured. A release names those public client ids in Gateway `appsettings.Production.json`. Local development names the same ids in `appsettings.Development.json`, and the release publish step removes that file. The auth host exchanges the code and returns an id token; Gateway checks the token and stores the durable link as provider plus subject. The first social sign-in on an uninitialized appliance creates the admin only when it presents the single-use setup token written to the local runtime directory. The access-token signing key in that directory is restricted to the Gateway process owner. External sign-in state is short-lived (five minutes), single-use, and bound to an HttpOnly, SameSite=Lax browser cookie. The callback returns both the authorization code and broker ticket; Gateway sends the broker ticket and the session-held return origin with the code exchange. Explicit link intent records the initiating user and completion requires that same authenticated user; it cannot silently sign in as a different linked account. A loopback connector sign-in finishes only in the browser that started it. The gateway database and each agent journal are restricted to that same owner. The channel host database is restricted to the ChannelHost process owner. After setup, a social sign-in works when that provider and subject are already linked, when the signed-in owner connects the provider, or when the person redeems a single-use invite code. Invites snapshot the canonical email and expire after seven days; redemption requires an exact canonical email match and consumes the invite in the same SQLite transaction that inserts the external link. Google invite redemption requires its verified-email claim. Microsoft ID tokens do not normally provide an email_verified claim, so invite matching trusts the canonical email claim in the signature-validated Microsoft token; this assumes that claim is the invitee address. Email is not the durable external-login bind key. Microsoft links also store tenant id and object id. Local username and secret phrase remain a separate sign-in method. An invite may be email-only; that account has no local secret until one is set. The refresh cookie is marked Secure only for HTTPS or a hop that arrived through the trusted WebHost listener. Sign-in, refresh, setup, and external login each have their own attempt budget per client. Gateway uses a single `X-Forwarded-For` address only when the connection is loopback or has no remote address; any other connection is limited by its own remote address. A login body with a null username or password is rejected before the secret check. A missing or malformed JSON body is rejected as a client error. WebHost does not proxy `/api/internal/**`. A connector test resolves stored secrets only for an accessible saved connector whose destination matches the stored definition. A personal HTTP address stored for that connector is used as the destination, and system-scoped credentials are not sent with it. The caller's own connector credentials still are. An unsaved probe requires connector-import permission, does not receive stored secrets, and is refused when it targets a loopback, link-local, private, carrier-grade NAT (100.64.0.0/10), or IPv6 unspecified address unless the caller is an admin. The probe resolves the name before connecting, refuses a name that does not resolve, and does not follow a redirect. A container or local probe runs for at most 30 seconds. Probe environment overrides cannot replace PATH, the dynamic loader, interpreter startup, or proxy variables. IPv4 addresses written as IPv4-mapped IPv6 are checked as IPv4. Password setup redeems the same single-use setup token. A named-user credential resolve omits system credentials and refresh-token or DPoP keys unless that caller opts in. Discovery metadata writes require connector management permission. Workspace file reads and listings do not follow a symlink or junction, and a hard link is refused on Windows and Linux. Conversation attachment downloads and files attached to a chat turn use that same open. A tool result can attach a file only when that file is inside the acting agent's workspace. Skill scripts, skill resources, and saved mail view files use that same open. Staging a skill package does not follow a link out of the package. An imported archive entry whose name is a Windows reserved device, or that ends with a dot or space, is rejected. Skill instructions are read with that same open. On Windows, a path segment that is a reserved device name, that contains a colon, or that ends with a dot or space, is rejected before Windows path normalization, so a trailing dot cannot collapse onto another file or the internal workspace directory. A Windows short name that expands into that internal directory is rejected after expansion. A system-scoped agent keeps a separate host workspace directory for each acting user. Manager accepts those directories as separate workspaces for the same agent scope, and still rejects two workspaces that use one host path. A signed-in user can read the platform runtime limits used when authoring an agent. Log level, observability, update channel, workspace root, sandbox image, and document ingestion remain on the admin system-settings read. Opening an HTML, SVG, or XML workspace file renders it in a sandboxed frame that cannot run script or reach the signed-in page. An access token whose signature is the wrong length is rejected. A channel delegation whose request digest is the wrong length is denied. A connector runtime environment override cannot replace PATH, the dynamic loader, interpreter startup, or the proxy variables on the host process that starts the container. A user-scoped connector call from a non-admin uses that same private-address check on every connection, including after a redirect, while a redirect to a public host is still followed. Gateway does not map the channel ingress or outbox HTTP routes; ChannelHost delivery stays on its capability-checked stream. Staging a skill into a workspace refuses a symlink or junction anywhere on that workspace path, so a link created from the sandbox is not followed into another host directory. A non-admin personal address for a system connector uses the private-address check on every connection. A container image without a registry path is trusted only when its name is one of this appliance's kautuka- images; a short registry name such as python:latest still requires a digest pin. A connector environment override cannot set the home directory, temporary directory, container-runtime configuration, or container socket on the host process that starts the container. A Slack file download is fetched only from slack.com or a host under that name, so a lookalike host such as notslack.com does not receive the bot token. A Slack upload URL is posted only to that same host, so the file is not sent to a lookalike. A Slack socket is opened only with wss on that same host. A channel approval test uses a session only when that session belongs to the channel owner. An agent runs a connector or skill only when that resource is system-scoped or owned by the acting user, and a user-scoped connector bundle is mounted only into that owner's agent workspace. An exposed agent is invocable as a tool only when it is system-scoped or owned by the acting user. A shared agent's remembered facts are injected into a chat only for the user who owns those facts. Two agents whose names reduce to the same workspace id keep separate scope ids and host directories, so one colliding name cannot make Manager reject every workspace update. A workspace id formed from one username and agent name is not reused when another username and agent name reduce to that same id. A client certificate is accepted for an internal service only when it chains to that service's local CA, so a self-signed certificate that copies the Gateway name is refused. A non-admin cannot create or replace the built-in docs skill, including by a different letter case, so that save cannot become a system skill. A skill id whose letters differ only by case cannot read or delete another skill's package directory. Skill attachments use exact skill ids. Empty, duplicate, or case-variant ids are rejected when building skill indexes. A skill script is read from the skill package, not from the copy staged in the agent workspace, so a command running in that workspace cannot replace the script that receives the skill's credentials. A workspace directory is chosen from the agent id and its owner id, and that directory stays put when another agent with the same name is added, renamed, or removed. An id that would otherwise collapse onto another id, such as one underscore versus a dash, keeps its own directory. Workspace resolution and attachment access use the current directory layout directly. The pre-release platform does not move legacy workspace directories or attachments, or create migration tracking records. An agent id is matched exactly, including letter case, so a second agent whose id differs only by case cannot take the first agent's workspace or runtime. A connector id is matched the same way, so a second connector whose id differs only by case cannot stop workspace publication or take the first connector's call. A workspace id that would be longer than Manager allows is stored as a fixed hash of the owner id and agent id, so one long agent id cannot make every later workspace update fail. Workspace paths derive from stable agent and owner identities; display-name changes and abandoned name-based directories do not change the selected workspace. A login for an unknown username still runs the password check, so the response time does not reveal whether that username exists. A sandbox environment file is created with owner-only access before the secret values are written, so another account cannot open it while it is still being filled. The gateway signing key, the machine key, and the setup token are written the same way, because those files live in a directory other local accounts can traverse. A credential recovery snapshot and its restore staging directory are owner-only before the plaintext vault is written, so another account cannot read the credential database from the shared temporary directory. The Windows installer page receives a one-time token, and install, uninstall, folder selection, and exit require that token, so a page in another browser tab cannot drive those actions. The installer also accepts a request only when its host is 127.0.0.1 or localhost, so a name that merely resolves to that address cannot read the token. A Windows short name is resolved to the real directory name before a workspace file is opened, so the short name of the internal workspace directory cannot be used to read it. A connector image reference must be one line, so a name that starts like a local kautuka- image cannot add further build instructions. A workspace move from an older directory name stays pending until that move finishes, and a later start retries the recorded source directory, so a failed move does not leave the existing files behind. A running sandbox, sidecar, or connector is replaced when its live mounts, network, environment, security options, or image no longer match the spec, and the health page lists each replacement. Those drift notes are returned only to an administrator, and a failed replace does not include the runtime error text. A workspace mount matches only when the observed path is that workspace path, or that path under a Podman Machine or WSL drive root, so a different parent directory is replaced. An environment entry that names a process loader or startup hook is replaced unless that exact assignment is part of the spec. A sandbox or connector that is privileged, that has a host device attached, or that joins the host process, IPC, user, or cgroup namespace is replaced. A resolved bind is replaced unless it is the workspace mount. A sandbox or connector whose network is not the sandbox network, or that publishes a host port, is replaced. A sidecar port with an extra host binding is replaced. A sidecar whose host mounts are not the declared volumes is replaced. A sidecar environment entry that names a process loader or startup hook is replaced unless that exact assignment is part of its spec. A sidecar that is privileged, that has a host device attached, or that joins a host namespace is replaced. A provider API key is stored as a system credential, and a later save does not copy an older catalog copy of that key back into the provider settings. On Windows, a connector command argument that contains a quote or a line break is rejected before Podman is started, because that command is launched through cmd.exe and a quote can start another command on the host. A percent sign in that argument is rejected for the same reason, because cmd.exe expands it from the process environment before Podman runs. A connector environment value cannot set CONTAINERS_HELPER_BINARY_DIR, because Podman searches that directory first for helper programs it runs on the host. It also cannot set STORAGE_OPTS, because Podman runs the program named by overlay.mount_program from that setting. A public request whose path uses a dot segment to reach /api/internal is rejected, because the proxy otherwise collapses that path before Gateway sees it. A tool catalogue is kept for the acting user and that user's connector address, and a cached connector tool is offered only when that user may still use the connector. A skill id that differs only by letter case cannot be saved beside the existing id. Tool catalogues reject ambiguous skill identities instead of selecting a compatible record. Skill packages are loaded only from their canonical directory under the current skill store. The installer bootstrap response does not include the action token. The installer window receives that token only in its launch address, and a headless run prints it only on that process console. A session whose target type names an agent, in any letter case, is created only when the caller can use that agent, and an attachment upload into that session requires the same check. A chat, workflow, or schedule run uses an agent id only when that agent is still system-scoped or owned by the acting user, so a reused id does not run someone else's agent. A container tool list proceeds once the container runtime is ready, so agent sandbox startup does not fail that list after thirty seconds. An expired approval command includes that decision, so the approvals page can clear the card instead of failing the response parse. A retained attachment blocks deletion only for the user who owns that chat session, so the same file name in another user's workspace can still be removed. A chat attachment upload cannot use the agent-output origin, so that label cannot skip the executable upload check. The telemetry sidecar joins its own container network, so a sandbox on the agent network cannot open its container port, and a copy still joined to the agent network is replaced.

## Internal service transport

Gateway calls Manager, CredentialsHost, ChannelHost, and UpdateService over HTTPS HTTP/2 with locally issued client certificates. CredentialsHost additionally binds the active Gateway client thumbprint/subject and performs capability checks for runtime resolution, own-user, cross-user, and system administration.

Every agent execution path uses one Gateway readiness guard before the assistant runtime is built. Gateway distinguishes a failed Manager status RPC from Manager-reported Podman failure; the latter is exposed as the `container_runtime` dependency. Desired-state reconciliation remains an internal execution gate and does not impersonate a service outage. CredentialsHost is checked independently. A real dependency failure becomes a typed canonical run failure that projects as Narad `run.failed`. Deny, cancel, and stop decisions remain available during an outage because they terminate work without executing an agent. The authenticated readiness endpoint exposes the same sanitized dependency state to the UI.

Manager issues distinct Gateway and UpdateService client certificates. Its server interceptor maps the exact certificate common name to an allowlist of RPC methods: Gateway receives the workspace, sandbox, connector, diagnostics, desired-state, and status methods it uses; UpdateService receives only `Ping` and `GetHostStatus`. Unknown identities and unknown methods fail closed. ChannelHost requires a scoped caller identity and an explicit `channels.read`, `channels.write`, `channels.runtime`, or `channels.ingress` capability on every non-health RPC. UpdateService still trusts any client certificate chained to its local service CA for its whole RPC surface.

## Credential storage

CredentialsHost encrypts credential values with AES-GCM and associated data containing scope, subject, key, and envelope identity. Vault key files, the credential database, and the machine key are restricted to the process owner, and a recovery key that other users can read is refused. A sandbox environment file is restricted the same way before it is passed to the container. The local CA private key and an outbound channel asset are restricted to the process owner. SQLite mutations, idempotency receipt, and audit commit together. Key rotation is checkpointed and old keys retire only after verification. Backup/restore requires an external recovery key outside the service root.

Provider mutation and resolution writes API keys under CredentialsHost keys such as `provider.<id>.api_key` rather than catalog JSON. The forward-only Gateway schema has no provider-secret table or startup hydration path.

Channel provider secret fields are deterministic CredentialsHost references. Gateway writes and resolves the encrypted user credential, then hydrates ChannelHost over its capability-authorized runtime RPC. ChannelHost keeps decrypted values in process memory only and rejects secret-valued attachment settings at both RPC and persistence boundaries. Startup drops the obsolete plaintext attachment schema rather than importing it.

## File data at rest

Agent workspace files and conversation attachments are ordinary files under the per-agent workspace. Gateway applies path authorization, upload type and size policy, and host file permissions, but the file bytes are not application-encrypted. The sandbox must be able to read and modify the mounted workspace directly, so encrypting individual workspace files inside Gateway would either make them unusable to agent tools or require distributing a decryption key into the sandbox. Conversation attachments share that workspace boundary and may also be parsed by a separate ingestion process.

Kautuka therefore relies on encrypted storage below the filesystem boundary for these files: BitLocker for the selected Windows/WSL storage location, or LUKS/dm-crypt (or an equivalently encrypted managed volume) for `/var/lib/kautuka` on Linux. Backups and snapshots containing the shared state root or agent workspaces require encryption and access controls of their own. Kautuka does not currently detect or enforce host-volume encryption, so this remains a deployment requirement rather than an application guarantee.

Application-level file encryption is deliberately deferred until there is a key lifecycle that covers rotation, recovery, background document parsing, sandbox access, and existing plaintext migration. The CredentialsHost envelope is scoped to small credentials and must not be reused as an ad hoc bulk-file key service.

## Workload containment

Manager canonicalizes workspace paths, requires strict descendants of the configured root, and rejects traversal through existing reparse points. The workspace host root is `Kautuka:Workspace:BaseRoot` when set; otherwise it is `<visible-root>/workspaces` (`~/.kautuka` in development, `/var/lib/kautuka` in production). An agent id is stored only when that id remains a single directory name under the agent state root. A padded, case-variant, or rewritten id cannot open another agent's journal. A system agent sandbox is mounted at that user's own workspace directory, not the parent directory that contains every user's folder. Attachment reads reject a link in any parent of the file, and a rejected hard link is not truncated. An attachment download also requires access to that session. A non-admin cannot save or test a private connector destination, point a connector URL override at one, or name a bundle file outside the managed bundle directory; an admin-saved system connector can still use one. Sandboxes run non-root with dropped capabilities, `no-new-privileges`, PID limits, read-only root filesystem, writable `noexec`/`nosuid` tmpfs charged to a bounded container memory cgroup, and CPU controls. The base sandbox image contract includes `/usr/bin/bash`; skill scripts written to tmpfs are passed explicitly to that fixed interpreter, never made executable, and removed by exit/signal traps. A skill script timeout is capped at that agent's sandbox max timeout; a missing or non-positive timeout keeps the sandbox default. A skill package import does not replace an existing skill unless the caller can manage that skill. A skill metadata save keeps only that skill's own package directory, and deleting the skill removes only that directory. A skill id that does not remain that directory name is not staged or deleted. A user-scoped skill receives only that user's credentials for its declared environment keys. A system-scoped skill can still receive system credentials. A user-scoped connector follows the same rule for its declared environment keys, and a system-scoped connector can still receive system credentials. The connector and skill rows store that scope and owner, so a later read does not turn a user-owned package into a system package. External images require immutable SHA-256 digests. First-boot infrastructure images (sandbox `FROM`, sidecar upstreams, mapped MCPB base) must also appear on `runtime-images.json`, which is published inside the Manager payload and listed as `runtimeImages` on the ECDSA-signed platform release. Manager loads mirrored OCI archives from `<shared-state>/oci-images` before pulling so a registry dropping an old manifest cannot take the runtime down. User/catalog connector images remain digest-pinned until package admission; Cosign is not used.

Connector isolation selects a private container and optional read-only agent-file mounts from accepted desired state. Every managed container joins the `kautuka-sandbox` network so aardvark can resolve sidecar aliases (`kautuka-pkgs-proxy`) and public DNS. Isolation is not `--network none`. MCPB wrapping a new tool still has to fetch npm/PyPI through that alias: language-package install is `podman run --network kautuka-sandbox` plus `podman commit`, not a host-netns `podman build` `RUN`, and the install command line pins `--registry` / `--index-url`. Runtime `npx`/`uvx` connector launches pin the same index flags from Gateway env and drop a caller `--registry`, `--userconfig`, `--globalconfig`, or `--index-url`. They do not forward another spelling of `npm_config_registry`, a caller npm or pip config file, or `PIP_CONFIG_FILE`. A managed CPython for `uv` (when the bundle pin does not match Fedora) is not an npm/PyPI package and does not go through pkgs-proxy. The sandbox image’s `uv` wheel uses the pkgs-proxy path. Gateway never probes `registry.npmjs.org` from the host, refuses `ManagerProxy:Mode=upstream`, and strips `PIP_EXTRA_INDEX_URL`, `UV_EXTRA_INDEX_URL`, and `UV_INDEX`. Gateway passes stable IDs and operation inputs; Manager owns host paths and container specifications. An isolated connector (`OwnContext`) is not given the agent workspace. When a tool returns file bytes beside a view, Manager writes them under that workspace at `view-files/{id}/{name}` and removes the bytes before the gRPC response. The journal keeps the relative path. Those view files can be downloaded when the code sandbox is disabled; other agent files cannot. Microsoft 365 mail and Google mail sign in with authorization-code PKCE. The release build sets `Kautuka:ConnectorAuth:Host` to `https://auth.kautuka.io`. That host inserts the client id and, for Google, the client secret. The PKCE verifier stays on the appliance. The browser returns through `https://auth.kautuka.io/callback`, and the appliance redeems the code. Hosted sign-in returns an opaque `krt1.<kid>.<iv>.<ciphertext>` refresh-token envelope bound by the broker to its provider and DPoP key thumbprint. Gateway stores that envelope unchanged in CredentialsHost, keeps the private DPoP key there, and never passes the refresh credential to the connector process. On refresh, Gateway sends the envelope unchanged to the broker and proves possession of the matching key for the actual broker token endpoint. Each proof, including a nonce retry, has a fresh `jti`; a server nonce is required when challenged. Disconnect submits the envelope to the broker's DPoP-protected key-revocation endpoint, retries a nonce challenge with a new proof, and deletes local credentials only after broker revocation succeeds. A legacy hosted refresh token without the `krt1` shape is not sent to the broker; the Connectors page asks the owner to reconnect and permits local removal with provider-permissions guidance. Direct local OAuth remains separate and uses the developer's own provider client. Hosted broker behavior was not deployed or live-validated here. A source checkout leaves the host unset and uses the developer's own OAuth app, with the loopback redirect `http://127.0.0.1:<port>/api/connectors/oauth/callback`. Those client files stay uncommitted. The sign-in host program is not in this repo. On Linux, Manager sets writable sidecar host-volume directories to owner and group `rwx` only (never world-writable); nested entries keep their existing modes so container-mapped UIDs are not rewritten. Writable mounts use Podman's `:U` option so non-root image users (for example git-pkgs/proxy `USER 1000`) can write without opening the host directory to world. After `:U`, the host path may be owned by a subordinate UID; Manager treats chmod failures on that path as non-fatal so recreate is not blocked.

Agent SuperExec is a separate host-command permission. Its modes are `disabled`, `ask`, and `trusted`. New or updated agents omit or blank `superExecMode` as `disabled`: the tool is unavailable until an owner explicitly chooses `ask` (HITL) or `trusted`. Existing persisted values are unchanged.

## Release trust

UpdateService and the Windows installer require ECDSA/SHA-256 detached manifest signatures and artifact SHA-256 before staging or import. A release id must be a single path segment before it is joined onto a staging, backup, or version directory. Sources must be `https` or loopback `http`. Missing signature URL, missing public key, invalid signature, or missing/mismatched hash fail closed. The same signed platform release lists first-boot `runtimeImages`; those digests are the authorization set Manager admits for infrastructure images.

Development may set `Update:AllowUnsignedLocalFeeds=true` (see `appsettings.Development.json`) for unsigned local feeds. Production forces that flag false. Signed loopback feeds remain valid under fail-closed verification.

## Channel durability

ChannelHost commits normalized ingress and provider cursors to SQLite before exposure. Gateway consumes this stream at least once and acknowledges only after its ingress pipeline completes; unacknowledged events replay after disconnect or either process restarting. Provider event IDs are unique in the outbox, so Telegram polling replay and Slack reconnect replay remain idempotent.

Telegram identity binding uses the owner-configured numeric private-chat ID. Gateway persists that non-secret destination only on the owner's attachment, and ChannelHost admits Telegram ingress only when both the external user ID and conversation ID exactly match the configured value. A caller cannot use the configured ID to cross an attachment, owner, tenant, or registration boundary; outbound work is delegated as the authoritative attachment owner rather than as a system worker.

Provider setup follows the same secret boundary. The browser sends new credentials to Gateway, which stores them in CredentialsHost and gives ChannelHost only the resolved runtime values over the authorized internal RPC. Provider validation results are reduced to bounded, sanitized status codes and safe official setup links. Provider response bodies, tokens, and incoming command text are not written to ordinary logs.

Channel lifecycle transitions remain owner-scoped and capability-authorized across the Gateway-to-ChannelHost boundary. Suspension removes runtime credentials and blocks new traffic while retaining durable evidence. Recovery returns the attachment to inactive; provider-native provisioning must validate the replacement configuration before it can become active. Terminal deletion is administrative because deterministic attachment IDs cannot currently replace a deleted tombstone safely.

### Channel boundary control traceability

| Threat or privileged effect | Enforcement owner | Denial/no-side-effect evidence | Operational evidence and residual risk |
|---|---|---|---|
| Wrong local workload or CA-issued peer | ChannelHost TLS admission: exact CN, URI SAN, purpose, chain, validity, and admitted thumbprint | `ChannelHostTrustBoundaryTests` | Certificate decision/reason and privacy-safe thumbprint; host administrator remains trusted |
| Missing, expired, replayed, or modified delegation | Channel request authorizer plus durable replay-token store | `ChannelHostTrustBoundaryTests`, `ExternalChannelProcessHarnessTests` | Issuer, audience, operation, key ID, token hash, digest, and reason; compromised Gateway issuer remains capable within its policy |
| Cross-owner, tenant, registration, conversation, or thread substitution | ChannelHost server-side operation/resource matrix and durable interaction binding | `ChannelHostTrustBoundaryTests`, `ChannelIngressServiceHardeningTests` | Hashed actor/tenant/request identities and exact policy reason; raw identity and content are excluded |
| Caller-supplied capability escalation | ChannelHost rejects non-empty authority-free capability fields | `ChannelHostTrustBoundaryTests` | Method and operation policy decision; wire field exists only for migration and has no authority |
| Forged or copied provider interaction | Provider adapter authentication plus exact durable callback binding | `ChannelIngressServiceHardeningTests`, `ChannelAdapterConformanceMatrixTests` | Sanitized interaction/registration/conversation hashes; provider compromise cannot become Kautuka authority |
| Credential disclosure | CredentialsHost owns encrypted persistence; ChannelHost accepts operation-scoped runtime material only | `ChannelAttachmentSecretHandlingTests`, `GatewaySecurityBoundaryTests` | Secret-canary scans and sanitized errors; ChannelHost compromise can use credentials already present in memory |
| Duplicate or uncertain outbound effect | Scoped operation digest and `RESERVED`/`EFFECT_STARTED`/`COMPLETED` state machine | `ChannelHostTrustBoundaryTests`, `ChannelAdapterConformanceMatrixTests` | Idempotency hash, state, lease and provider marker; Telegram cannot prove every uncertain effect |
| Ingress replay or stale ACK | Stable provider event ID plus durable lease generation | `ChannelIngressServiceHardeningTests`, `ChannelAdapterConformanceMatrixTests` | Cursor, event hash, lease generation and ACK result |
| Runtime continuation initiated by transport | Gateway approval/wait state machine is the only continuation authority | approval continuation and channel ingress integration suites | Approval decision, source, wait generation, continuation claim and canonical event range |
| Simulator endpoint admitted in production | ChannelHost startup profile admission | provider transport profile tests | Profile, sanitized endpoint identity and environment; Production fails before workers start |

For every denial, the test is complete only when it proves that no adapter call, credential resolution, state mutation, ACK, continuation, or provider effect occurred. The canonical event catalogue classifies runtime-event privacy and consumers; ChannelHost delivery evidence remains separate from runtime truth.

Production process isolation enforces the same boundary below the application protocol. Linux and WSL installations run Gateway and ChannelHost as distinct system principals and system units, with ChannelHost ordered before Gateway. Gateway owns only its client and delegation private keys; ChannelHost owns only its server private key. Each private directory is owner-only and each private file is readable only by that service UID. Public trust inventories are separate and read-only. The root-run bootstrap deletes its staging CA key, upgrades preserve the runtime inventories, and installer preflight refuses missing, unexpected, incorrectly owned, or over-permissive material before either service starts.

The legacy shared local bootstrap is permitted only when the host is explicitly running in Development. Production startup has no fallback to that layout: missing production-root configuration or an invalid runtime inventory is a terminal readiness failure, not a reason to mint new trust material under a service identity.

## Logging and diagnostics

Hosts use shared `ILogger`/OpenTelemetry configuration. The platform policy is to log identifiers and measurements rather than prompts, tool inputs/results, tokens, credentials, or command text; Gateway also has explicitly configured diagnostic content-capture settings that must remain opt-in and protected. RPC failures should be typed and sanitized.

Tool execution failures follow that boundary. Gateway persists and projects a fixed public failure code/message instead of exception text. The execution log records agent, session, run and tool-call identifiers, tool name, public failure code, and exception type; it does not record the exception message, tool arguments, or tool result. Narad receives a typed, versioned failure envelope on `tool.call.finished`, so the UI can explain the failure without exposing sandbox, connector, credential, or provider diagnostics.

WebHost binds loopback HTTP by default. A configured non-loopback listener fails startup unless a PKCS#12 TLS certificate is loaded. The proxy removes hop-by-hop headers and client-supplied forwarding headers, adds forwarding metadata from the accepted connection, streams response bodies, and returns a fixed cache-disabled JSON error without downstream exception details. A response that has already started is never replaced with an error body. Browser responses set nosniff, deny framing, and send no referrer.
