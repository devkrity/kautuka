> Every Kautuka-owned outbound network flow must traverse the central gateway. No supported component, container, helper, bootstrap operation, update operation, or recovery path may bypass it. Connector-specific restrictions are required for feature completion; more detailed execution attribution is supplementary.

**Terms used in this spec.**
- **Network gateway**: the central, logical enforcement point described here (routing, firewall, admission, DNS policy, audit and accounting). It is a root-owned network namespace plus the services that run in it, not necessarily a container.
- **Gateway service**: the existing `Kautuka.Gateway` process (API, agents, approvals, ownership). The two are different things. "Gateway" alone is not used.
- **Core owner / workload owner**: the two rootless Podman accounts of AD6 (`kautuka-core`, `kautuka-work`). **Core domain** and **workload domain** are the containers each owns.
- **Release module**: the part of Manager that took over UpdateService's responsibilities (§8).
- **Network service**: the root-owned service that builds the topology and runs the network gateway (§5.2). The **policy service** is its admission, DNS and accounting part, written in C# Native AOT (§5.9).
- **Workload namespace**: a network namespace that holds one Kautuka component or runtime domain (Manager, the core owner's engine and helpers, the workload owner's engine and helpers, bootstrap) and whose only external route is the network gateway.
- **Flow**: one conntrack entry (TCP connection, UDP association, or ICMP exchange) from a workload namespace towards any destination outside it.

## 0. Summary

Revision 4 fixes the deployment shape and the order of work. Kautuka's application services move into containers now: Gateway service, WebHost, ChannelHost, CredentialsHost and the sidecars. No production installs exist, so nothing has to be migrated in place (AD5). The host keeps only Manager, Podman and its helpers, systemd supervision, a small privileged service that sets up namespaces and the firewall, and any packet-admission shim. Gateway policy and admission, DNS, and the durable audit run as independent local infrastructure. They do not depend on any application starting, and they keep cached last-known-good artifacts.

Core services and untrusted connectors and sandboxes run under **separate rootless Podman owners**, each with its own storage, home and runtime directories, subordinate ID ranges, engine and control sockets, volumes and secrets (AD6). Releases are signed transactions over immutable image digests, enforced by an installed Podman trust policy. They are staged in full, activated through a journal, and recovered without downloading anything (AD7). UpdateService's job becomes a distinct module inside Manager.

The work runs as four sequential **stop gates** (AD8). Gate 1 covers gated acquisition and closed failures, plus a small WSL smoke check. Gate 2 covers two connectors with different policies. Gate 3 covers the release transaction and recovery. Gate 4 covers WSL integration and phone access. Work stops at the first gate that fails. Per-connector enforcement is still required before the feature counts as complete.

Everything in revision 3 that still holds is kept: the invariant, the network gateway, central DNS, durable admission, asynchronous approvals, fail closed, and AD1 to AD4.

**What changed from revision 3**
1. New §1 **Deployment shape** (AD5, AD6), with CredentialsHost on `--network none` (§1.5), the Manager API and Podman socket rules (§1.6), and the chosen base image `mcr.microsoft.com/dotnet/runtime-deps:10.0-azurelinux3.0-distroless`, pinned by digest, with its globalization, UID and no-shell consequences checked against the code (§1.7).
2. New §6 **Start order and health**, §7 **Ingress and platform**, and §8 **Release transaction and artifact acquisition** (AD7).
3. **Core-service identity is now also hidden by rootless translation.** Gateway service, ChannelHost and WebHost become containers behind the core owner's rootless helper. Revision 3's "one host namespace per service" no longer gives a proven source per service on its own, so the pre-translation mechanisms of §5.7 now apply to core services as well (§5.1).
4. Revision 3's per-connector source addresses inside the Gateway service (rev 3 §4.7.6 (b)) do not survive rootless translation once the Gateway service is a container. The option is replaced (§5.7.6).
5. Revision 3's migration and four-phase rollout (rev 3 §15) are replaced by the four gates (§19). The "Linux appliance with host units" install path becomes a developer and test path only.
6. Revision 3's §10 (bootstrap) is revised for container-first. Minimum gateway and recovery artifacts ship locally, so a pull never needs a gateway that is not yet running (§14).
7. New data model tables for the release manifest and the activation journal (§12). Threat model, diagrams, checklist and open questions are updated. Open questions are renumbered with a mapping from revision 3 (§23.3).

**Key contradictions at `5ca94f0` with the container-first shape** (full list in §18, rows Y1-Y17): the installer deploys native host systemd units and never uses the existing service Dockerfiles. One service user owns every container: sidecars, connectors and sandboxes share one Podman storage. UpdateService is a separate service that drives a root `apply-release` helper over `sudo`. The signed release manifest describes a native tarball, not image digests, and no Podman trust policy is installed. Connector `podman run` has no `--pull=never`, so a missing image is pulled implicitly. Socket directories are host tmpfiles with group-based access, which must be re-proven under rootless user-namespace mapping. Telemetry uses TCP on loopback. Manager's API accepts free-form images, commands, arguments, environment, host bundle paths, and shell commands for sandboxes. Units use `Type=exec`, so "started" is reported as "ready".

## 1. Deployment shape (AD5, AD6; decided in revision 4)

Container-first application deployment is decided now. There are no production installs, so the shape can change without in-place migration. The host layout at `5ca94f0` (§4.1) becomes a developer and test path only.

### 1.1 Placement

| Layer | Runs as | Contents |
|---|---|---|
| **Host (trusted base)** | host processes under systemd | Manager (rootless, its own account); the two rootless Podman owners and their helpers (§1.3); systemd supervision; `kautuka-netd`, the small privileged namespace and firewall provisioning service (§5.2, §5.9); any packet-admission shim (the NFQUEUE consumer, §5.6) |
| **Local network infrastructure** | host processes, or specially managed containers with no dependency on application startup | Gateway policy and admission, the central resolver, the durable audit store (§5.5-5.6, §11). Each keeps **cached last-known-good artifacts**: binaries or images, the bootstrap policy and the last activated policy version. They can start when no application container exists and no network fetch is possible. |
| **Host maintenance path** | root, invoked rarely | A small, separately versioned path that can repair or replace Manager, Podman, the guest (WSL distro or VM), and the network infrastructure. It does not depend on Manager or any application container (§14.4). |
| **Core application containers** (core Podman owner) | containers | Gateway service, WebHost, ChannelHost, CredentialsHost, sidecars (OpenObserve, pkgs-proxy) |
| **Workload containers** (workload Podman owner) | containers | Connector pods, agent sandboxes, skill execution, Kautuka-built and third-party connector images |

- **UpdateService's responsibilities move into Manager as a distinct module**, the *release module*. It covers verification, compatibility checks, staging, activation, recovery and audit (§8). The separate UpdateService process, its gRPC service (`src/shared/Kautuka.UpdateService.Protos/Protos/updateservice.proto:8-14 @5ca94f0`) and its `sudo apply-release` path (`src/backend/Kautuka.UpdateService/Hosting/UpdateServiceIntegration.cs:119-132 @5ca94f0`) are retired. Gateway service keeps the update UI and calls the release module through Manager's constrained API (§1.6).
- **Core services are not put in one pod.** Containers in one pod share an SELinux label and namespaces, which would remove the separation between, for example, CredentialsHost and WebHost. Each core service is its own container with its own SELinux MCS categories.

### 1.2 Hardening of containerised services
Every core container:
- runs as a **non-root identity** inside the container, mapped to a distinct subordinate UID of the core owner;
- has **all capabilities dropped** (`--cap-drop ALL`, `no-new-privileges`) and none added;
- has a **read-only root filesystem**, with writable space only in explicitly listed volumes and `tmpfs` (no wide host bind mounts);
- has **resource limits** (memory, CPU, pids);
- runs under a **seccomp profile** (Podman default or tighter) and **SELinux confinement** with per-container categories, where the platform has SELinux (Fedora WSL rootfs and Fedora/RHEL hosts; Q53);
- is started by digest, never by tag (§8.3), with `--pull=never` (§8.5).

The base image and its consequences are in §1.7. The existing service Dockerfiles are the starting point: `src/images/kautuka-gateway/Dockerfile:15-18 @5ca94f0`, `src/images/kautuka-channel-host/Dockerfile:15-18 @5ca94f0` and `src/images/kautuka-credentials-host/Dockerfile:15-18 @5ca94f0` already build distroless images. WebHost has none yet (§18 Y2).

### 1.3 Separate runtime accounts (AD6)
Core application services and untrusted connectors and sandboxes have **separate rootless Podman owners**:

| Separated item | Core owner `kautuka-core` | Workload owner `kautuka-work` |
|---|---|---|
| Container storage and configuration (`storage.conf`, `containers.conf`, `policy.json`) | own | own |
| Home and runtime directories (`$HOME`, `XDG_RUNTIME_DIR`) | own | own |
| Subordinate UID/GID ranges (`/etc/subuid`, `/etc/subgid`) | non-overlapping with every other account | non-overlapping with every other account |
| Engine socket (`podman system service`) and control sockets | own, reachable only by Manager | own, reachable only by Manager |
| Data volumes and secrets | core volumes, credential vault, mTLS material | workspace volumes, per-connector env |
| Network namespace for helpers (§5.2) | `kautuka-ns-core` | `kautuka-ns-work` |

Rules:
- Workload containers **never** receive core service storage, credential volumes, or core control sockets (the Gateway, Manager or CredentialsHost sockets).
- Manager's cross-domain orchestration goes through a **narrow, authenticated interface** (§1.6). It validates permitted images, mounts, namespaces and lifecycle operations. It is not an arbitrary command runner.
- Each owner's engine runs as its own system unit (`User=kautuka-core` or `User=kautuka-work`, `NetworkNamespacePath=`), so pulls, builds and helpers spawned by that engine inherit that owner's namespace. The network gateway sees two separate runtime domains as proven sources.

**Limits of the claim, stated plainly.** The split reduces what an attacker gains after escaping into the workload account's context. It does not contain a successful host-kernel compromise. Manager remains trusted to orchestrate both domains. These limits do not weaken the case for making the split now.

### 1.4 Identity of core services at the network gateway
Core containers sit behind the core owner's rootless helper. As with connectors (AD3), the helper opens fresh sockets, so the network gateway sees only the `core` runtime domain. Per-service policy (ChannelHost may reach Slack and Telegram; WebHost and CredentialsHost may reach nothing) therefore needs a pre-translation mechanism from §5.7.2. Candidate B, a per-container helper with a bound outbound address, is the natural fit for a handful of long-lived core containers. CredentialsHost needs none, because it has no network (§1.5).

### 1.5 CredentialsHost
- Runs with **`--network none`**. It serves gRPC over a Unix socket only. It has no network interface except loopback inside its own namespace.
- **Three storage surfaces:**
  1. **private vault volume**, mounted only into CredentialsHost;
  2. **small socket directory**, mounted into CredentialsHost and the Gateway service only. The Gateway service gets the socket directory, **never the vault**;
  3. **explicit maintenance access** for backup, restore and key recovery. Today these are CLI modes of the same binary (`src/backend/Kautuka.CredentialsHost/Program.cs:54-65 @5ca94f0`), run as a one-off maintenance container with the vault mounted. They are never a standing mount in another service.
- **To verify:** the mapped UID and GID of the socket file as seen by the Gateway service container (rootless user-namespace mapping), parent directory permissions (today `2750` with a `-client` group, `scripts/kautuka-install-linux.sh.in:1064-1106 @5ca94f0`, `src/shared/Kautuka.Hosting/Hosting/KautukaHostNetworkPolicy.cs:225-243 @5ca94f0`), the SELinux label of the shared directory, and replacement of a stale socket on restart (`src/shared/Kautuka.Hosting/Hosting/KautukaKestrelTransport.cs:30-33 @5ca94f0`, `ClearStaleSocket`).
- **Keep authenticated gRPC** (mTLS over the socket, `src/shared/Kautuka.Hosting/Hosting/KautukaKestrelTransport.cs:15-18 @5ca94f0`). File permissions are not the only gate.
- **Readiness and telemetry without a network interface:** readiness is the gRPC `GetHealth` call over the socket (`src/shared/Kautuka.CredentialsHost.Protos/Protos/credentialshost.proto:19 @5ca94f0`) or a Podman healthcheck that runs inside the container. Telemetry goes to a Unix-socket exporter or a file-backed spool that a collector reads, not to TCP `127.0.0.1:20215`.
- **Limits:** this does not protect against a compromised Manager, which orchestrates the container and its mounts. Nor does it protect against misuse through the authorised Gateway-service link, since the Gateway service can request resolved credentials (`src/shared/Kautuka.CredentialsHost.Protos/Protos/credentialshost.proto:20 @5ca94f0`).

### 1.6 Manager API and the Podman sockets
- **The Podman engine sockets are never exposed** to the Gateway service, WebHost, connectors or sandboxes. Only Manager holds them.
- **Manager's API accepts constrained operations only.** Each request names a known operation: start a connector from an approved image digest, call a tool, stop, probe, exec in a sandbox, or a release-module action. Manager validates the image against the approved set, mounts against an allowlist per domain, namespaces (no `host`, no `container:` into another domain), capabilities (none added), and the lifecycle state. Free-form Podman arguments are never accepted.
- At `5ca94f0` the API is mTLS-authenticated with per-method authorisation by client certificate name (`src/backend/Kautuka.Manager/Grpc/ManagerClientAuthorizationInterceptor.cs:17 @5ca94f0`, `src/backend/Kautuka.Manager/Grpc/ManagerClientAuthorizationInterceptor.cs:59-69 @5ca94f0`). That stays. But connector messages carry free-form `image`, `command`, `args`, `environment` and a host `bundle_path` (`src/shared/Kautuka.Manager.Protos/Protos/manager.proto:289-302 @5ca94f0`), and `Exec` takes a free-form `command` and `environment` (`src/shared/Kautuka.Manager.Protos/Protos/manager.proto:40-45 @5ca94f0`). Under AD6 these must be validated as described above. `Exec` is acceptable only because it runs inside a workload-domain sandbox; it must never target a core container (§18 Y9).

### 1.7 Base image for containerised services *(rev 4; chosen by Amit)*
- **Base:** `mcr.microsoft.com/dotnet/runtime-deps:10.0-azurelinux3.0-distroless` for the Gateway service, WebHost, ChannelHost and CredentialsHost. Manager stays on the host. In the release manifest the image is **pinned by digest** (`runtime-deps@sha256:…`) per architecture, never by tag (§8.1, §8.3).
- **What the image implies:**
  - **Distroless:** no shell, no package manager, no `curl` or `wget`. Nothing at runtime may need a shell. Container healthchecks must be exec-form and use either a **built-in subcommand** of the service binary (for example `Kautuka.Gateway --probe-ready`, which connects to the service's own Unix socket and calls its readiness endpoint) or a **readiness socket / `sd_notify`** (`--sdnotify=container`).
  - **Non-root by default:** user `app`, UID **1654**. Inside each container the UID maps to a subordinate UID of the core owner. If every core container keeps the default 1654 under the same owner's mapping, all of them map to the **same host-side UID**. File-level separation between services (vault, socket directories, data volumes) would then rest only on SELinux labels and mounts. Each service therefore gets a distinct in-container UID (`--user <uid>:<gid>` per service) or a distinct user-namespace range (`--userns=auto` with per-container sizes), and its socket directory and volumes are owned by that mapped ID (Q57, Q36).
  - **Globalization:** the plain `runtime-deps` distroless image contains no ICU and no tzdata. The `-extra` variant (`runtime-deps:10.0-azurelinux3.0-distroless-extra`) adds ICU and tzdata. A .NET app that does not set `InvariantGlobalization` and finds no ICU fails at startup. With no tzdata, `TimeZoneInfo.FindSystemTimeZoneById` throws `TimeZoneNotFoundException`.

## 2. Goals, non-goals and milestones

### 2.1 Goals
- **G1 Coverage.** Every outbound flow from a Kautuka-owned process, container or helper crosses the network gateway, to the internet and to LAN or private addresses alike (§5.1).
- **G2 Below application code.** Routing and enforcement are done by the kernel under a root-owned service. No application is responsible for routing (§5.2-4.3).
- **G3 Universal controls.** Policy by proven source, destination address, protocol and port, explicit private, link-local, metadata and host access, and connection and rate limits; domain rules with stated guarantees (§5.4).
- **G4 Central DNS** with query policy and answer validation (§5.5).
- **G5 Durable audit.** An admission record exists before any packet of a flow is forwarded (§5.6, §11).
- **G6 Connector enforcement.** Each connector has a trustworthy policy identity and its own restrictions are enforced (AD3, §5.7).
- **G7 Ownership-aware policy and approvals** following system and personal ownership, narrow-only for users and agents, approvals that never hold a connection (§9, §10).
- **G8 Fail closed** in every failure, restart, update and recovery path (§13, §14).
- **G9 Plain-language Network activity view** per connector and per agent (§11.3).

### 2.2 Non-goals
- No TLS decryption, CA injection, proxy variables or mandatory SDK transport changes.
- No payload inspection or data-loss prevention. An allowed destination can still be used to exfiltrate (§16.3).
- No per-URL-path rules.
- No control over Windows, the upstream WSL networking stack, or the host OS's own traffic (package updates of the distro, time sync, the user's other software). The boundary is Kautuka's Linux processes and their namespaces (AD2).
- No inbound policy beyond keeping today's inbound interfaces working (`docs/adr/0004-channel-gateway-productization.md:20 @5ca94f0`).
- No switch to rootful Podman (AD1).
- No in-place migration of existing installs (none in production; AD5).
- macOS in this release (requirements recorded in §7.3).

## 3. Architectural decisions and release criteria

These eight decisions are binding. AD1-AD4 come from revision 3 and still hold, with the notes marked *rev 4*; AD5-AD8 are new. Each ends with its release criteria; §22 collects them as a checklist.

### AD1. Preserve rootless Podman; namespace prototype failure is a stop condition
- *Rev 4 note:* under AD5 and AD6 the host keeps Manager and **two** rootless Podman owners. The managed namespaces are `kautuka-ns-manager` (Manager), `kautuka-ns-core` (core owner's engine, helpers, pulls, builds) and `kautuka-ns-work` (workload owner's). Each engine runs as a system unit with `User=` and `NetworkNamespacePath=` (§1.3), so this decision applies to each of them. The application services are containers, so the "user unit" problem (§18 X1) now concerns Manager and the two engines only.
- **Preferred design.** A managed network namespace (`kautuka-ns-manager`) contains Manager and every process that can open network connections on its behalf: `podman` subprocesses, `conmon`, the rootless network helper (pasta or slirp4netns), `aardvark-dns`, `rootlessport`, image pulls, image builds (including `RUN` steps executed by buildah), image loads, and any socket-activated or timer-started Podman service.
- **Prototype question.** Can Manager run as a *system-managed* unit with `User=kautuka`, `NetworkNamespacePath=/run/netns/kautuka-ns-manager`, and the delegation it needs (`Delegate=yes`, a cgroup subtree it owns, `XDG_RUNTIME_DIR`, D-Bus where Podman's systemd cgroup manager needs it)? The whole login session need not move, but **every launch path must be accounted for** (§4.10). An existing user manager (`user@<uid>.service`) or helper left outside the boundary cannot be overlooked: if it can start a process that opens a socket, it must either be inside the boundary or be proven unable to reach the network.
- **Fallback rules.**
  1. Per-UID host firewall rules (`meta skuid`) are acceptable only as a **bypass-denial backstop**. They are not an equivalent replacement for the network gateway. Owner matching covers locally generated traffic; it does not by itself establish coverage of forwarded container traffic.
  2. A redirect-based alternative (for example, host-namespace rules that redirect the service user's traffic into the network gateway) is acceptable only after separately proving that it preserves the same mandatory central route, audit and controls.
  3. **No automatic switch to rootful Podman.** That changes the isolation model and needs a separate architectural decision and explicit approval.
  4. If neither rootless arrangement satisfies the requirements, **that platform's release is blocked pending redesign.**
- **Release criteria.** R1.1 Manager and all launch paths in §4.10 run inside managed namespaces on each supported platform. R1.2 A direct-bypass test (§20.2) from every launch path fails. R1.3 Podman stays rootless (`podman info --format '{{.Host.Security.Rootless}}'` = true).

### AD2. WSL is named in the release gate
- Validation is required on **both** supported Linux **and** the shipped WSL configuration.
- For WSL, the boundary is Kautuka's Linux processes and their namespaces. Windows and the upstream WSL networking stack are outside it. The requirement is that Kautuka traffic crosses the network gateway *before* it reaches that upstream stack.
- Initial target: the currently supported **WSL NAT** configuration. Mirrored networking stays unsupported unless separately validated (it is already rejected by the monitor, `src/installer/Kautuka.Monitor.Core/WslConfigDrift.cs:101-111 @5ca94f0`).
- A Linux-only release is an explicit scope decision, never a fallback hidden behind "platform limitations".
- WSL tests must include rootless helper placement, DNS, IPv6, service restarts, updates, and attempts to reach the Windows host or leave by an alternative route (§20.3).
- **Release criteria.** R2.1 All §20 suites pass on supported Linux and on the shipped WSL image. R2.2 Mirrored mode is detected and refused. R2.3 If WSL is not shipped, the release notes say so as a scope decision.

### AD3. Per-connector controls are on the critical path
- Milestones in §2.3. Gate 2 (§19) establishes connector enforcement, which is required; only additional attribution is optional.
- A pod forwarder, or another trusted mechanism that binds identity **before rootless translation**, is a valid candidate (§5.7). Do not assume nftables marks, socket marks or cgroup matches survive pasta or slirp4netns translation into newly opened sockets: the helper opens fresh sockets as the Manager user, and the original packet's metadata is gone.
- Whatever mechanism is chosen must bind the connector identity to the traffic reliably (§5.7.1 requirements).
- **Acceptance test (concrete).** The mail connector can reach its approved Microsoft endpoints, cannot reach an unapproved destination, and cannot borrow another connector's broader permissions (§20.5).
- **Release criteria.** R3.1 The acceptance test passes on Linux and WSL. R3.2 Every connector type (Kautuka-built, MCPB bundle, third-party image, remote MCP) has a documented identity path that passes the borrowing test.

### AD4. Userspace admission stays off the established-flow path
- NFQUEUE remains a candidate implementation. Intended behaviour:
  - userspace evaluates a new flow and **durably records its admission**;
  - explicitly admitted flows then use kernel forwarding and accounting;
  - policy revocation removes the relevant permission **and terminates affected flows**;
  - queue absence, queue exhaustion or admission-service failure **never** enables unrestricted forwarding (no `bypass` / fail-open flag on the queue rule).
- conntrack `NEW` does not mean exactly one packet. Retransmitted SYNs and early packets (TCP Fast Open data, UDP bursts) can belong to a still-pending flow. Admission needs a **bounded pending-flow table, deduplication and defined timeouts** (§5.6.3).
- The prototype measures: new-flow admissions per second, admission latency, established-flow throughput, CPU and memory use, queue saturation, and recovery during policy-service restarts. It must also define whether previously admitted flows continue during a restart under a bounded, still-valid grant (this spec proposes yes, §5.6.5); pending, unadmitted flows stay blocked.
- The first SYN has no TLS SNI. First-packet admission can enforce source, IP, protocol and port policy. Stronger hostname decisions need an established DNS binding or an inner inspection or proxy mechanism that withholds application traffic until its decision (§5.4.2).
- **Release criteria.** R4.1 Prototype numbers recorded against the targets in §21. R4.2 Fault-injection tests (§20.6) show no unadmitted packet forwarded when the queue is absent, full or its consumer is killed. R4.3 Revocation stops external forwarding for affected flows within the stated bound, and no queued packet is released against a revoked policy or identity generation (rev 4.1; endpoint resets are optional and tested separately).

### AD5. Container-first application deployment
- Gateway service, WebHost, ChannelHost, CredentialsHost and the sidecars run as containers. The host keeps Manager, Podman and its helpers, systemd, `kautuka-netd`, and any packet-admission shim. Network policy and admission, DNS and audit are independent local infrastructure with cached last-known-good artifacts. A small host maintenance path can repair Manager, Podman, the guest and the network infrastructure (§1.1).
- UpdateService is folded into Manager as the release module (§1.1, §8).
- Core services keep non-root identities, dropped capabilities, read-only filesystems, limited writable mounts, resource limits, seccomp and SELinux. They are not grouped in one pod (§1.2).
- **Release criteria.** R5.1 No application service runs as a host process in a release build. R5.2 Every core container passes the hardening checks of §1.2 (`podman inspect` assertions). R5.3 Network infrastructure starts and enforces with no application container present.

### AD6. Separate runtime accounts are mandatory
- Core application services and untrusted connectors and sandboxes have separate rootless Podman owners, with separate container storage and configuration, home and runtime directories, non-overlapping subordinate UID/GID allocations, engine and control sockets, and data volumes and secrets (§1.3).
- Workload containers never receive core service storage, credential volumes or core control sockets. Manager's cross-domain orchestration uses a narrow, authenticated interface that validates permitted images, mounts, namespaces and lifecycle operations, and is not an arbitrary command runner (§1.6).
- Limits: this reduces what an attacker gains after escaping into the workload account's context. It does not contain a host-kernel compromise, and Manager remains trusted for both domains.
- **Release criteria.** R6.1 Two owners with disjoint `subuid`/`subgid` ranges, storage, runtime directories and sockets (automated check). R6.2 No workload container has a mount, socket or secret of the core domain (`podman inspect` over all workload containers). R6.3 Manager rejects requests outside the permitted image, mount, namespace and operation sets (negative tests, §20.12).

### AD7. Releases are signed transactions
- Signed manifest of immutable digests, architecture, minimum Manager and runtime versions, and persistent-state compatibility. Installed Podman trust policy enforces verification. Containers run by digest. The full set is staged before any service stops. No independent auto-updates. The last working set is protected from GC. Activation is journaled with defined power-loss behaviour. Migrations are backward compatible or use a deliberate backup/restore or forward-recovery path. Old data is never automatically restored after the new version has accepted writes. Readiness is distinct from "container started" (§8).
- **Release criteria.** R7.1 A tampered manifest, an unsigned image and a tag reference are each refused (by the release module and by Podman policy independently). R7.2 Power loss injected at every journal phase recovers as in §8.6 without network access. R7.3 An incompatible image/data combination is never started.

### AD8. Stop-gate sequencing
- The work proceeds through four sequential gates (§19). **Stop at the first failed gate.** Downstream features are not built around an unproven network boundary.
- Gate 1 includes a small WSL feasibility smoke check of the namespace, firewall and packet-admission primitives. Full WSL integration and phone access are Gate 4.
- Per-connector enforcement (AD3) remains a completion requirement. It is established in Gate 2.
- **Release criteria.** R8.1 Each gate's result is recorded with evidence before the next gate starts. R8.2 No release ships unless all four gates passed on its platforms.

## 5. Target architecture

### 5.1 Mandatory coverage (design point 1)

#### 5.1.1 What must be covered
Every one of these sits in a workload namespace whose only external route is the network gateway:

| Workload | Workload namespace *(rev 4)* | Policy subject (proven source) |
|---|---|---|
| Manager (runtime controller and release module) | `kautuka-ns-manager` | runtime domain `manager`: release metadata only, if any (artifact fetches are done by the engines, §8.5) |
| Core owner's engine, helpers, pulls, builds | `kautuka-ns-core` | runtime domain `core`: artifact-fetch policy for core images (§8.5) |
| Gateway service container | inside the core owner's rootless namespace | component `gateway` via a pre-translation identity (§1.4, §5.7) (purposes: remote MCP, model provider, mail OAuth, auth broker, sign-in, catalog, update UI through Manager) |
| WebHost container | same | component `webhost` (no outbound; published inbound port only, §7.1) |
| ChannelHost container | same | component `channelhost` (Slack, Telegram) |
| CredentialsHost container | `--network none` | none: it has no interface (§1.5) |
| Sidecars (OpenObserve, pkgs-proxy) | same as Gateway service | components `telemetry` (no upstream), `pkgs-proxy` (npm, PyPI) |
| Workload owner's engine, helpers, pulls, builds | `kautuka-ns-work` | runtime domain `work`: artifact-fetch policy for approved connector images and Kautuka bases |
| Connector pods, remote MCP pods, agent sandboxes, skill execution | inside the workload owner's rootless namespace | runtime domain `work` plus a connector or sandbox identity from §5.7 |
| Local network infrastructure (policy, DNS, audit) | `kautuka-ns-gw` | itself: upstream DNS only |
| Host maintenance path, guest maintenance | `kautuka-ns-bootstrap` | bootstrap or maintenance identity (§14) |

"Proven source" means the network gateway knows the subject from *where the packet came from* (which veth, which address the network service assigned), never from anything the workload says about itself. Additional identity inside a runtime domain comes from §5.7.

#### 5.1.2 Destinations
- Internet and LAN or private destinations are treated the same: both must cross the network gateway and both need policy. **There is no private bypass.** RFC 1918, ULA, CGNAT `100.64.0.0/10`, link-local, the host's own addresses, the WSL Windows host, and cloud metadata `169.254.169.254` / `fd00:ec2::254` are denied unless a rule explicitly allows them (§5.4.1).
- Filesystem Unix sockets and other local IPC (pipes, shared files) stay local and are not routed. Abstract Unix sockets are scoped by network namespace; none were found in `src/shared/Kautuka.Hosting/Hosting/KautukaHostNetworkPolicy.cs @5ca94f0` at baseline, and the prototype must confirm that nothing Kautuka depends on uses them across components (D-Bus user buses, `podman` API, systemd notify).

#### 5.1.3 Loopback TCP interfaces that must change
Because loopback is per namespace (§4.2). *Rev 4:* with core services as containers, the same applies between containers and the host:
- **Telemetry:** OpenObserve's OTLP endpoint moves to a Unix socket (preferred, if the exporter supports it) or to an appliance-internal address that is reachable from workload namespaces through the network gateway under a local-only rule `component:* → telemetry:5080`. Either way the flow is admitted and accounted, but it never reaches the uplink.
- **WebHost edge:** the only published port (§7.1). It is published by the core owner's engine and forwarded from the host by the network service (DNAT on the host side for `127.0.0.1:20229` needs `route_localnet`, or a small root-owned socket relay; Q8). LAN listeners get the same treatment. This is inbound and is not an outbound policy decision, but replies must not open a path out.
- **Optional TCP service transport:** unsupported under enforcement, or routed between workload namespaces through the network gateway with local-only rules.
- `src/backend/Kautuka.Manager.RuntimeContainer/Hosting/ApplianceHostExposureAssert.cs:64-79 @5ca94f0` must be updated to check the new places.

### 5.2 Enforcement below application code (design point 2)

A root-owned **network service** (`kautuka-netd.service`, system unit, starts before every other Kautuka unit; step 1 of §6.1):
1. creates the network gateway namespace `kautuka-ns-gw` and one workload namespace per row in §5.1.1, as named namespaces under `/run/netns`;
2. creates one veth pair per workload namespace, with the peer in `kautuka-ns-gw`, assigns addresses from a private appliance range (for example `10.231.0.0/24` and `fd7a:6b74::/64`, configurable to avoid clashes, Q7), and sets each workload's only route to the network gateway's address on that veth;
3. connects `kautuka-ns-gw` to the host uplink (a veth to the host namespace with masquerade on the host side, or a macvlan/ipvlan where supported) and loads nftables in `kautuka-ns-gw` with default-drop `forward` and `input`;
4. loads a deny-all table in each workload namespace (only the veth and `lo`; no other interfaces can be created because workloads lack `CAP_NET_ADMIN` in that namespace's owning user namespace);
5. starts the policy service (admission, DNS, accounting) inside `kautuka-ns-gw`.

Host processes (Manager, the two Podman engines, maintenance) join their namespace through systemd: `NetworkNamespacePath=/run/netns/kautuka-ns-<name>` with `After=`/`Requires=kautuka-netd.service` and `BindsTo=`, so a stopped network service stops them too. Containers inherit their engine's namespace through its rootless helper. Filesystem Unix sockets keep working, including socket directories bind-mounted into containers (§1.5).

The kernel forwards permitted traffic. Userspace sees only new-flow admission (§5.6) and DNS (§5.5).

### 5.3 Transparency (design point 3)
- **No proxy environment variables.** The connector deny list (`src/backend/Kautuka.Manager.RuntimeContainer/Hosting/ConnectorContainerSpecBuilder.cs:121-142 @5ca94f0`) stays; host units get none.
- **No per-connector network configuration** inside the connector. Connectors see an ordinary default route and resolver.
- **No TLS interception and no CA.** SNI may be read without decrypting (§5.4.2), never altered.
- **No mandatory SDK transport changes.** Every client in §4.6 works unchanged. Application handlers *may* add identity (§5.7.6) but are never responsible for routing; deleting such a handler must not open a path out.
- **No escape via another protocol or raw sockets.** The workload namespace has one route; the network gateway's `forward` chain is default-drop for every family and protocol (§5.4.3). Raw sockets, if a workload somehow had `CAP_NET_RAW`, still produce packets that must cross the same chain.

### 5.4 Universal controls and domain rules (design point 4)

#### 5.4.1 Controls every rule can use
- **Proven source:** component or runtime domain (§5.1.1), and inside the `work` domain the connector or sandbox identity (§5.7).
- **Destination:** IP address or prefix, IPv4 and IPv6.
- **Protocol and port:** TCP and UDP ports; ICMP types.
- **Explicit special destinations:** `private` (RFC 1918, ULA, CGNAT), `link_local`, `metadata` (`169.254.169.254`, `fd00:ec2::254`, plus a configurable list), `appliance_host` (host and WSL Windows host addresses), `loopback_of_host`. Each is denied unless a rule names it, and each grant is shown separately in the UI.
- **Connection and rate limits:** per source, concurrent flows and new flows per second (nft `limit`/`meter` before the queue, and quota in the policy service, §5.6.6).

#### 5.4.2 Domain rules with honest guarantees
An **IP/port rule** authorises an endpoint. A **domain rule** authorises a name, and must state how the name is established and bound to the flow. Revision 3 defines three binding levels:

| Binding | How the name is established | What it guarantees | Where available |
|---|---|---|---|
| `dns_bound` | The flow's destination IP was returned by the central resolver to **the same source** for an allowed name, within the answer's TTL (bounded, for example min(TTL, 300 s)) | The client asked for the allowed name and connects to an address the resolver gave it. Does not prove the server is that name. | All TCP and UDP, first packet (works with first-SYN admission) |
| `sni_bound` | An inner inspection step reads the TLS ClientHello SNI (or HTTP/1.x `Host`) before any application byte is forwarded, and the address is in the resolver's answers for that SNI | The client claims the allowed name in TLS, and the address belongs to it | Only where an inspection proxy withholds traffic until the decision (§5.7.2 candidate A; not on the kernel fast path) |
| `ip_only` | No name | Endpoint only | Everywhere |

- **Strict policy** (default for connector rules and for `ask` mode): if the required binding cannot be established, the flow is **denied**. For example, a connection to an IP literal that no allowed lookup returned **to that source** is denied under a domain rule. *Rev 4.1:* a numeric connection to an address that the same source already obtained through an allowed DNS binding (within its lifetime) is indistinguishable at this layer and **is** admitted under `dns_bound`; that is exactly the `dns_bound` guarantee above, no more.
- **Residual risks, stated plainly:**
  - **Shared IPs and CDNs.** A `dns_bound` grant for `allowed.example` on a shared front end also reaches every other tenant on the same IP for its lifetime. `sni_bound` narrows this but cannot see a different inner HTTP `Host` (domain fronting).
  - **ECH.** With Encrypted Client Hello the visible SNI is the front end's public name, not the hidden destination. *Rev 4.1:* the outer name **never satisfies a strict rule** naming the hidden destination. When the ClientHello carries an ECH extension and the rule requires the inner name, the flow is denied (`ech_inner_name_unavailable`), unless the subject holds an explicit, separately displayed **front-end permission** (for example "may reach the Cloudflare ECH front end `cloudflare-ech.com:443`"), which is recorded as a weaker endpoint grant.
  - **IP literals** with no prior allowed binding for that source cannot satisfy a domain rule; they need an IP rule. A literal equal to an address the source already received for an allowed name does satisfy `dns_bound` (indistinguishable at this layer).
  - **Non-TLS protocols** (SSH, SMTP, databases) have no SNI; only `dns_bound` or `ip_only` apply.
  - **An allowed destination does not prevent exfiltration.** A mail connector allowed to reach Microsoft Graph can send data to an attacker-controlled mailbox through it.

#### 5.4.3 Protocol and family handling
- **TCP**: admitted per flow.
- **UDP**: DNS to the central resolver only, by default. **QUIC (UDP 443) is denied**; clients fall back to TCP. Other UDP only with an explicit rule (each admitted as a flow with its own timeout).
- **ICMP/ICMPv6**: only what is essential: `RELATED` errors for admitted flows (destination unreachable, packet too big, time exceeded) and IPv6 neighbour discovery on the veth. Echo is denied unless allowed.
- **IPv6**: handled with the same policy as IPv4 from the first release. If an install has no IPv6 uplink, workloads still get IPv6 denied at the network gateway (and `disable_ipv6` on the workload veth as belt and braces), never an unfiltered route.
- **Everything else** (SCTP, GRE, ESP, raw IP protocols, multicast, broadcast) is dropped.

### 5.5 Central DNS (design point 5)
- Every workload namespace's resolver points at the network gateway address on its veth (host units through a bind-mounted `resolv.conf` set by the network service, or `systemd-resolved` disabled for those units). Inside the rootless namespace, aardvark keeps answering container names; non-container names reach the central resolver through the rootless helper's DNS forwarding to Manager's `resolv.conf` (to be verified per helper and version, Q5). Podman's documentation says aardvark on an `--internal` network answers `NXDOMAIN` for non-container names; the prototype must test that behaviour on the shipped Podman and netavark versions on Linux and WSL, and the design must not depend on aardvark forwarding.
- Other DNS (UDP/TCP 53 to any other address, DoT 853, known DoH endpoints) is subject to ordinary policy and denied by default. DoH to an unknown HTTPS host cannot be recognised without decryption; it is covered only by the destination policy for that host.
- The resolver applies **query policy** per source (allowed names or suffixes for that subject, denied names), sends queries only to **constrained upstreams** (configured resolvers on the uplink, never a resolver chosen by the workload), **validates answers** (drops answers that put private, link-local, loopback or metadata addresses behind a public name unless the subject has the matching special grant; this is the rebinding defence), caps answer TTLs used for bindings, and records `(source, name, answers, ttl)` as DNS bindings (§12).
- **A DNS permission never creates unrestricted forwarding.** Resolving a name only creates a short-lived binding that a domain rule may use. Without a matching rule, the flow is still denied.
- DNS tunnelling through query names is limited by per-source query policy and rate limits; it is recorded but not prevented for allowed suffixes.
- *Rev 4.1:* **DNS-policy denials can raise approvals.** When query policy denies a name for a subject in `ask` mode, the resolver answers `REFUSED` (or `NXDOMAIN`, per Q5) and emits a pending-approval event that identifies the **subject and the requested name** (and query type). It does **not** invent a destination port, because DNS does not reveal one. The approval (§10), if granted, allows the name for that subject with the ports declared for it in the connector's manifest, or with port 443 only if the approver explicitly chooses it on the card. A later connection still needs a matching rule and binding.

### 5.6 Durable admission (design point 7, AD4)

#### 5.6.1 Pipeline (candidate: nftables + bounded NFQUEUE)
In `kautuka-ns-gw`:
1. `ct state established,related` with a valid admission mark → `accept` and count (kernel fast path).
2. `ct state invalid` → drop.
3. Per-source `meter`/`limit` on new flows → excess dropped and counted (no queue entry).
4. `ct state new` → `queue num N ` **without** `bypass`. If no consumer is bound, the kernel drops the packet. This is the "fail-open disabled" requirement.
5. Everything else → drop.

The policy service reads the queued packet, looks up `(source subject, dst, proto, port, binding)` against the cached policy (§5.8), and:
- **deny**: issue **`NF_DROP`**, and count or record the denial (§5.6.4). *Rev 4.1:* a deny is **never** issued as `NF_ACCEPT` (for example "accept towards a reject rule"): an accepted queued packet resumes traversal at the **next base-chain hook**, not at the rule after the `queue` statement, so a denied first packet could escape unless another enforcement hook is defined. If prompt TCP rejection is wanted (so clients fail fast, as ask mode would like, §10), it is a **separate mechanism**, specified and tested on its own: for example the policy service sends a TCP RST to the source through a raw socket in `kautuka-ns-gw` after dropping, or a dedicated reject chain at a later hook that matches a per-flow "denied" mark set before the drop. Until that mechanism passes its own tests (§20.6), denial means silent drop.
- **allow**: write the admission record durably (§5.6.2), set `ct mark` / `ct label` with the admission and grant ids, then `NF_ACCEPT`.

```mermaid
sequenceDiagram
  participant W as Workload (any namespace)
  participant K as Kernel (kautuka-ns-gw nftables)
  participant P as Policy service
  participant S as Admission store
  participant U as Uplink
  W->>K: SYN (ct NEW)
  K->>P: NFQUEUE (no bypass)
  P->>P: pending-flow table: dedup 5-tuple
  P->>P: evaluate cached policy vN (source, dst, proto, port, DNS binding)
  alt allowed
    P->>S: INSERT admission (fsync)
    S-->>P: ok
    P->>K: set ct mark/label = admission, grant; ACCEPT
    K->>U: forward SYN
    W->>K: further packets (ct ESTABLISHED, marked)
    K->>U: kernel forward + counters (no userspace)
    K-->>P: conntrack DESTROY event (bytes, end)
    P->>S: UPDATE completion, bytes
  else denied or store unavailable
    P->>K: NF_DROP (prompt reset only via the separate mechanism)
    P->>S: record denial or bump bounded counter
  end
```

#### 5.6.2 Durability
- The admission record (§12 `network_admissions`) is persisted with a synchronous commit **before** the verdict is issued. Completion time, last-seen time and byte counts are updated later from conntrack destroy events and periodic counter reads.
- If the policy service crashes after admission but before completion is written, the record stays `completion = unknown`, with the last-seen time from the most recent counter sweep.
- If the audit store is unavailable, full, or above its high-water mark, **new admissions are refused** (deny with reason `audit_unavailable`). Established, already-recorded flows continue.

#### 5.6.3 Pending-flow table
- Keyed by the conntrack tuple (and zone). A retransmitted SYN or another early packet of a pending flow is deduplicated: held in the queue up to a small per-flow cap, then dropped; it does not trigger a second evaluation.
- Bounded size (for example 4096 entries total and 64 per source). When full, new flows from that source are dropped and counted, never accepted.
- Defined timeouts: a pending entry not decided within 2 s is dropped (the client retransmits and gets a fresh decision); decided entries are kept for 5 s to answer late duplicates consistently.

#### 5.6.4 Denials
- Denied attempts are recorded as rows where practical (first denial per `(source, dst, port, reason)` per minute), and as **bounded counters** under floods (per source, per reason, per minute). The store cannot be exhausted by a scanning workload.

#### 5.6.5 Restarts and revocation
- **Policy-service restart.** Admitted flows carry a `ct mark` that the fast-path rule accepts as long as the grant id in the mark is in an nft set of still-valid grants. The set has element timeouts equal to the grant's remaining validity, capped at a short bound (proposal: 120 s). So previously admitted flows continue during a restart under a bounded, still-valid grant; new flows queue with no consumer and are dropped. When the service returns it reloads policy, re-validates the set and resumes.
- **Revocation** (rule removed, grant expired, connector disabled, approval revoked, identity revoked). *Rev 4.1:* two separate behaviours:
  - **Required:** external packet forwarding for affected flows stops within the revocation bound (R4.3, target ≤ 2 s from publication). The policy service removes the grant from the valid-grants set, so established packets of affected flows fall through to drop in both `forward` and `output`. It then deletes the conntrack entries (by mark/label), so later packets re-enter as `NEW` and are re-evaluated against current policy (and denied). Deleting conntrack state does **not** close endpoint sockets or send TCP resets; it only changes how later packets are classified.
  - **Optional:** the endpoints receive a prompt failure notification (a TCP RST to the workload side, and to the upstream where appropriate) through the separate reset mechanism of §5.6.1. It is not part of the security guarantee.
- **Revocation and pending admission race.** Every policy version and every runtime-identity registration carries a monotonic **generation**. A queued packet's decision records the policy and identity generations it was evaluated against. **Immediately before releasing a queued packet with an allow verdict** (after the durable record is written), the policy service checks that the current generations still permit it: the grant is still in the valid set, and the identity behind the source address or session has not been revoked or reassigned. Otherwise it issues `NF_DROP` and marks the admission record `revoked_before_release`. Late duplicate packets of a flow already decided (§5.6.3) follow the decision **as rechecked**, never the cached allow. An address or identity released by one pod is not reassigned until every flow and pending entry bound to it has been dropped or expired (reuse quarantine).
- Bounded continuation of previously admitted flows during a policy-service restart (above) is kept. On restart, the valid-grants set is re-validated against the current generation before new admissions resume.

#### 5.6.6 Quotas
Per source: concurrent admitted flows, new admissions per second, denial rows per minute, DNS queries per second. Over-quota is denied and counted.

#### 5.6.7 Alternatives to evaluate in the prototype
nftables + NFQUEUE (candidate); nftables sets populated ahead of time from policy and DNS bindings with no per-flow userspace step (fast, but cannot write the admission record *before* the first packet passes, so it fails G5; *rev 4.1:* recording from conntrack events does not fix that, because conntrack `NEW` events are emitted after the first packet has already been forwarded, Q12); eBPF (cgroup/tc) with a ring buffer (same durability issue). Under the current invariant only alternatives that hold the first packet until the record is durable are eligible. The choice is made from prototype numbers (§21), not in this spec.


#### 5.6.8 Traffic originating in the network gateway namespace *(rev 4.1)*
> Traffic originating in the network gateway namespace—including resolver and proxy upstream connections—has constrained OUTPUT policy and a durable admission record before external transmission.

- The pipeline in §5.6.1 covers forwarded traffic (the `forward` hook). The central resolver's upstream queries and candidate A's proxy upstream connections are opened by local sockets in `kautuka-ns-gw` and traverse `output`, not `forward`. The `output` chain in `kautuka-ns-gw` is default-drop. It allows only (a) resolver upstream to the configured resolvers on DNS ports, and (b) proxy upstream connections, and each new flow is queued for admission exactly like forwarded traffic, with no `bypass`.
- **Candidate A association and accounting.** For each connector connection accepted by the identity ingress, the policy service writes **one** admission record before the proxy opens its upstream socket. The record carries the connector identity (from the authenticated ingress session, §5.7.2), the ingress connection tuple **and** the upstream connection tuple, and the hostname source (`sni_bound`). The upstream socket is marked (`SO_MARK`) with that admission id, so the `output` admission of the upstream flow matches the existing record instead of creating a second one. Bytes are counted once, on the upstream flow (the externally visible traffic). The ingress-side leg is recorded as local, with no separate external byte count. A proxy upstream connection with no matching connector admission is denied. There is no "proxy-only" identity.
- Resolver upstream queries are aggregated: one admission per upstream resolver association (UDP five-tuple lifetime) attributed to the resolver, with per-query records in `dns_bindings` naming the requesting source. Queries forwarded for a source that has been denied are never sent upstream.

### 5.7 Connector identity (AD3)

#### 5.7.1 Requirements for any mechanism
1. The identity must be bound **before** rootless translation, or carried in a form that survives it.
2. The connector process cannot choose, change, read or replay its identity.
3. Identity is registered by Manager (trusted for runtime lifecycle and identity registration, §5.8) and is known to the policy service before the connector's first packet.
4. A connector cannot use another connector's identity, including after the other's pod is recreated (no reuse races).
5. Failure of the mechanism denies traffic; it never falls back to the broader `work` domain policy for connector destinations.
6. *Rev 4.1:* identity is not undermined by local paths: a connector cannot obtain another subject's external permissions through a local listener, shared service or shared writable state (§5.7.7).

#### 5.7.2 Candidates

| Candidate | How identity reaches the network gateway | Strengths | Weaknesses | Prototype must show |
|---|---|---|---|---|
| **A. Pod forwarder + PROXY v2** (rev2's forwarder, retargeted) | Each connector runs in a Podman pod on an `--internal` network. A Kautuka forwarder starts first, installs a redirect for all member TCP to itself, drops `CAP_NET_ADMIN`, and relays each connection to an **identity ingress** in `kautuka-ns-gw`. *Rev 4.1:* the forwarder-to-ingress hop is a **mutually authenticated, encrypted transport** (for example TLS 1.3 with client certificates, or an equivalent authenticated channel), and the ingress binds the authenticated peer credential to the **registered runtime identity** of that pod (Manager registers the credential's fingerprint with the pod identity, §5.7.1 item 3). The ingress maps token → connector, applies connector policy, reads SNI (`sni_bound`), and connects upstream. | Identity carried in-band, survives translation. Supports `sni_bound`. Recommendation: prototype **B** first (it keeps AD4's kernel path), **A** in parallel as the candidate that also gives `sni_bound`. *Rev 4.1:* B is a reasonable first experiment. Current pasta documentation describes binding outbound sockets to a source address (passt(1), `--outbound`), but that still needs proof with the shipped Podman and helper versions **and** the DNS path (whether the helper's DNS forwarding preserves the bound source). Helper source-address behaviour, DNS identity preservation, user-manager placement, mapped socket permissions, WSL kernel support and performance are left to the gates (§19). Choose per the §21 numbers and the §20.5 acceptance test.

#### 5.7.3 Pod lifecycle *(retained from rev2 §4.2, §6.3; still needed for A and B)*
- One pod per runtime key (user, connector, mode, scope), created on first call or reconcile; pods are per user already because the runtime key includes `user::connector` (`src/backend/Kautuka.Gateway/Infrastructure/Agents/McpAgentToolProvider.Proxy.cs:262 @5ca94f0`, `src/backend/Kautuka.Manager.RuntimeContainer/Hosting/WorkspaceContainerConnectorExecutionService.cs:1262-1281 @5ca94f0`).
- Candidate A order: pod create → forwarder (`CAP_NET_ADMIN` only until rules are installed; or a one-shot init container) → health → member with `--cap-drop ALL` and no network options. This removes the start-up race for `run --rm -i` members that are PID 1 (`src/backend/Kautuka.Manager.RuntimeContainer/Hosting/WorkspaceContainerConnectorExecutionService.cs:602-609 @5ca94f0`).
- Candidate B order: network service assigns and registers the address → Manager creates the pod with that helper address → member.
- Warm pods via the 600 s cooldown (`src/backend/Kautuka.Manager.RuntimeContainer/Hosting/WorkspaceContainerConnectorExecutionService.cs:893-907 @5ca94f0`); optional warm pool per connector.
- Stop, drift, orphan GC, shutdown and naming changes in §17.

#### 5.7.4 Correction to revision 2: serialising calls does not prove per-call identity
Rev2 §6.2 recommended P1 + P2 (one pod per runtime key, calls serialised per pod) to make per-pod tokens exact per call. That is wrong as a proof: a connector process can leave background processes or open sockets that keep running after call N returns, and their new connections during call N+1 are attributed to N+1. Therefore:
- **Connector enforcement** uses the per-pod identity (user, connector), which is exact regardless of concurrency. This is all the milestone needs.
- **Per-call attribution** (additional, optional) is claimed only where it can be proven, for example one pod per call. Otherwise rows show the pod identity and the set of calls active at the time, labelled "one of".
- *Rev 4.1:* revision 4 also listed per-call Linux UIDs (with processes killed before UID reuse) as proof. That is withdrawn. Killing processes before reuse addresses one problem, but not shared writable state or local listeners that relay work under another process's identity.

> Under enforcement, connectors execute in their own policy boundary. Shared agent sandboxes have a stable sandbox identity. UID-based attribution may be investigated, but UID assignment alone does not satisfy connector isolation or exact per-call attribution.

#### 5.7.5 Agent sandboxes and skills
An agent sandbox is one pod identity (user, agent sandbox). Shell commands and skills run in it, so skill-level rules can only be enforced at sandbox granularity unless skills move into their own pods (Q14). Connectors executed inside a sandbox (`src/backend/Kautuka.Manager.RuntimeContainer/Hosting/WorkspaceContainerConnectorExecutionService.cs:571-596 @5ca94f0`) inherit the sandbox identity, which **fails the borrowing requirement** (§5.7.1 items 4 and 6). *Rev 4.1:* the first implementation **disables connector execution inside the shared agent sandbox**. Under enforcement Manager refuses agent-sandbox mode for connectors and runs them in their own pods (§18 X7). The sandbox keeps its stable sandbox identity for shell and skills. Q15 is closed.

#### 5.7.6 Gateway-service connectors (remote MCP) *(rev 4)*
Remote MCP connectors are connectors, so AD3 applies. Revision 3 proposed per-connector source addresses bound by the Gateway service's `ConnectCallback` (rev 3 §4.7.6 (b)). **That no longer works:** the Gateway service is now a container behind the core owner's rootless helper, which opens fresh sockets from one address, so addresses chosen inside the container do not survive translation. Options:
- **(a)** Move remote MCP calls into a Kautuka-built connector pod in the workload domain (dc27869 review §4 option 2). Identity then comes from §5.7.2 like any connector. This also removes remote-MCP traffic from the core domain.
- **(b')** The Gateway service's `ConnectCallback` (`src/backend/Kautuka.Gateway/Domain/Connectors/ProbeNetworkPolicy.cs:71-86 @5ca94f0`) connects to the identity ingress of candidate A over the mutually authenticated transport of §5.7.2 (the Gateway-service container's own credential, bound to the `gateway` identity), with a PROXY v2 header naming the connector inside it. That is identity enrichment by an application handler, which design point 3 allows: without the handler, the flow gets only the `gateway` component policy, which includes no connector destinations.
Recommendation: (a), because it keeps all connector traffic in one domain with one identity mechanism. Use (b') only if (a) slips past Gate 2 (Q23). A compromised Gateway service can still misuse any connector it can call, since it holds every connector credential (§16.4).

#### 5.7.7 Lateral isolation (Gate 2 requirement) *(rev 4.1)*
Container-to-container traffic does not cross the network gateway, so without these rules a connector could reach another connector's listener, or an overly capable shared service, and have it connect externally under the broader permissions. That is permission borrowing, even though the external connection still crosses the central gateway.
- **Deny lateral connector access by default.** No connector pod can open a connection to another connector pod, agent sandbox, or core container. With candidate B each pod has its own namespace and no shared bridge. With candidate A the forwarder redirects every member TCP connection, so a lateral connection either goes to the ingress or is dropped, and the workload owner's internal network has inter-pod traffic denied (netavark isolation or per-pod networks; to prove in Gate 2).
- **Enumerate the permitted shared-service interfaces.** The first implementation permits exactly: (1) the package service (`kautuka-pkgs-proxy`) on its registry-protocol ports, for package installs during image materialisation and for sandboxes that declare it. At rev 4 the package service is a core-owner sidecar (§1.1), so this is the one permitted workload-to-core interface. Gate 2 decides how it is reached: a single published port that the workload namespace can reach and nothing else of the core namespace, or a separate workload-owned package-service instance (Q10); (2) the central resolver (§5.5); (3) for candidate A, the identity ingress. Nothing else. Any addition is a spec change.
- **Constrain shared services so they cannot act as general relays.** The package service serves only the npm and PyPI registry protocols for the configured upstream registries: no `CONNECT`, no arbitrary-URL fetch, no redirects to other hosts, and no user-supplied upstreams. Its own outbound policy (component `pkgs-proxy`) allows only those registries. A connector reaching it gains nothing beyond package downloads that its own policy may also be asked to allow.
- **Tests (Gate 2, §20.5):** permission borrowing through another connector (connector X opens a listener; connector Y tries to reach it and relay to a destination only X may reach), and through the package service (Y tries to fetch an arbitrary URL, use `CONNECT`, or follow a redirect to a destination outside its policy). Both must fail.

### 5.8 Local control and responsibilities (design point 8)

| Component | Responsible for | Not responsible for |
|---|---|---|
| **Network service / policy service** (root, `kautuka-ns-gw`) | Namespaces, veths, routes, firewall, DNS, admission, accounting, durable flow records, cached published policy, revocation | Ownership decisions, approvals UI, deciding who may change policy |
| **Gateway service** | Policy management (rules, modes, grants), ownership checks, approvals and their delivery, publishing policy versions, the Network activity UI and API | Routing, per-connection decisions |
| **Manager** | Runtime lifecycle in both domains through the constrained API (§1.6); trusted registration of container and pod identities (pod ↔ connector, source address or token, expiry); the release module (§8) | Policy decisions, approvals; arbitrary Podman commands |

- The policy service evaluates **cached published policy**. There is **no live call to the Gateway service per connection.** If the Gateway service is down, published policy keeps working; `ask` decisions are denials (§10).
- Policy is published as immutable, monotonically numbered versions over a Unix socket owned by the network service; the Gateway service writes, the policy service validates (schema, size, no widening beyond install approvals) and activates atomically. Each admission records the version used.
- Manager registers identities over a separate Unix socket. Registration can only bind a pod to a connector that exists in the current published policy and to the user in the runtime key; it cannot grant destinations.

### 5.9 C# Native AOT policy service (design point 10)
- The services already target .NET 10 with Native AOT: `src/backend/Kautuka.Manager/Kautuka.Manager.csproj:4 @5ca94f0` (`net10.0`), `src/backend/Kautuka.Manager/Kautuka.Manager.csproj:7 @5ca94f0` (`PublishAot`), `src/Directory.Build.props:10 @5ca94f0` (`PublishAot`), and the same in `src/backend/Kautuka.Gateway/Kautuka.Gateway.csproj:4 @5ca94f0`, `src/backend/Kautuka.Gateway/Kautuka.Gateway.csproj:16 @5ca94f0`, `src/backend/Kautuka.ChannelHost/Kautuka.ChannelHost.csproj:4 @5ca94f0`, `src/backend/Kautuka.ChannelHost/Kautuka.ChannelHost.csproj:7 @5ca94f0`, `src/backend/Kautuka.CredentialsHost/Kautuka.CredentialsHost.csproj:4 @5ca94f0`, `src/backend/Kautuka.CredentialsHost/Kautuka.CredentialsHost.csproj:7 @5ca94f0`, `src/backend/Kautuka.UpdateService/Kautuka.UpdateService.csproj:4 @5ca94f0`, `src/backend/Kautuka.UpdateService/Kautuka.UpdateService.csproj:7 @5ca94f0`, `src/backend/Kautuka.WebHost/Kautuka.WebHost.csproj:4 @5ca94f0`, `src/backend/Kautuka.WebHost/Kautuka.WebHost.csproj:8 @5ca94f0`.
- Split: a **small privileged layer** (`kautuka-netd`, root) exposing structured operations only (create namespace, create veth pair, set address, set route, load an nft ruleset from a typed model, delete conntrack by mark, add or remove set elements). **No arbitrary shell, no string-built `nft` command lines from untrusted input.** Netlink and nfnetlink are called through P/Invoke or a typed generated ruleset file validated before load. The **policy service** (admission, DNS, accounting) runs with only `CAP_NET_ADMIN` in `kautuka-ns-gw`, under its own UID.
- *Rev 4:* the release module inherits UpdateService's AOT code inside Manager. The privileged layer and the policy service are local network infrastructure: they ship as host binaries in the local last-known-good set, not as images that need a pull (§6.1).
- Tests run against the **published AOT binaries**, not only JIT test hosts: P/Invoke and netlink interop, source-generated JSON serialization (trimming), cancellation and shutdown paths, overload behaviour (queue saturation, store full), and signal handling.

## 6. Start order and health

### 6.1 Order
Each step starts only when the previous one is locally ready. Nothing in steps 1-3 depends on an application container.

| Step | What starts | Ready when |
|---|---|---|
| 1 | Host network boundaries: `kautuka-netd` creates namespaces and veths and loads **default deny** | Rulesets loaded and verified by hash. No route out exists yet. |
| 2 | Local policy and admission, central resolver, durable audit store | Bootstrap policy or last-activated version loaded from the local cache; audit store writable; queue consumer bound |
| 3 | Restricted artifact acquisition (the release module's fetch path, §8.5) | Admission rules for the artifact-fetch policy active |
| 4 | CredentialsHost | `GetHealth` over its socket |
| 5 | Gateway service | Local readiness (database open, Manager and CredentialsHost reachable) |
| 6 | WebHost, ChannelHost | Local readiness |
| 7 | Connector and agent workloads | Per-pod identity registered (§5.7), then member started |

**Avoiding the pull-needs-gateway deadlock.** The minimum artifacts needed for steps 1-6 ship locally and are never fetched at start: network infrastructure binaries, the bootstrap policy, and image archives of the active and last-working release, loadable with `podman load` (`src/backend/Kautuka.Manager.RuntimeContainer/Hosting/PodmanImageArchiveStore.cs:58 @5ca94f0`). A missing core image is a recovery case (§8.7), not a pull.

### 6.2 Health model
Four separate signals per service:

| Signal | Meaning | Used for |
|---|---|---|
| **Liveness** | The process is running and not wedged | Restart by systemd or Podman |
| **Local readiness** | The service can do its own work: storage open, sockets bound | Start order (§6.1) and the release module's activation check (§8.6) |
| **Dependency readiness** | Required local dependencies are ready (for example, Gateway service → CredentialsHost, Manager) | Display; gating of dependent steps |
| **External provider availability** | Slack, Telegram, model providers, remote MCPs reachable | Display and alerts only |

- **An external outage must not cause a restart loop or a rollback.** A Slack outage makes ChannelHost report "Slack unavailable". It stays live and locally ready, and the release module does not count it as a failed activation.
- **Readiness notification is distinct from "container started".** Core containers report readiness through `sd_notify` (`podman run --sdnotify=container`) or a healthcheck that tests local readiness. At `5ca94f0`, units are `Type=exec` (`scripts/kautuka-install-linux.sh.in:727 @5ca94f0`, `scripts/kautuka-install-linux.sh.in:928 @5ca94f0`, `scripts/kautuka-install-linux.sh.in:1027 @5ca94f0`), so systemd treats "exec succeeded" as started. The Gateway service exposes `/health` and `/alive` (`src/backend/Kautuka.Gateway/Hosting/GatewayAppBootstrap.cs:430-431 @5ca94f0`), and `apply-release` waits for `coreReady` (`scripts/kautuka-apply-release.sh:1201-1203 @5ca94f0`). That signal is reused as local readiness.

## 7. Ingress and platform

### 7.1 Ingress
- **Only WebHost is published.** It serves browsers on the desktop and on the user's phone over the LAN. Every other service has no published port.
- **ChannelHost** is reached only by the Gateway service, over its socket with authenticated gRPC. Network rules deny any other caller.
- **Channels use outbound polling or WebSocket only:** Telegram long polling and Slack Socket Mode (`src/backend/Kautuka.ChannelHost/Providers/Slack/SlackSocketModeWorker.cs:707 @5ca94f0`). No webhook endpoint exists in ChannelHost at baseline (repository grep). Any future webhook is received by WebHost and forwarded internally. It never gets its own published port.
- Published-port path: WebHost's port is published by the core owner's rootless engine in `kautuka-ns-core`. The network service forwards the host's chosen address and port (loopback for desktop-only, a LAN address for phone access) into that namespace. Replies follow the inbound flow's conntrack entry and never open an outbound path (Q8).

### 7.2 WSL
- **WSL NAT is tested explicitly**, including LAN and phone reachability of the WebHost path through Windows port forwarding (Q37 lists what is chosen), startup, restart, and helper placement (Gate 4).
- **DNS tunnelling must not bypass the controlled resolver.** If WSL's DNS tunnelling feature is on, it answers DNS through a Windows-side path. Workloads must still use only the central resolver; any other resolver address is denied (§5.5).
- The distro's base network namespace is shared with the user's other distros (§15.2), so nothing decisive lives there.

### 7.3 macOS (later; not in this release)
Requirements recorded now so the design does not preclude them: ARM64 images and ARM64 Native AOT builds (the release pipeline produces `kautuka-linux-amd64.tar.gz` only, `scripts/build-release-assets.sh:1668 @5ca94f0`); guest (VM) updates through the host maintenance path; sleep and resume (conntrack and grants after resume, clock jumps); VPN clients on the Mac changing routes; port forwarding into the guest for WebHost; LAN reachability for phones. **Secrets and sockets live on the guest's native filesystem, never on shared folders** (virtiofs or 9p do not preserve Unix socket semantics, ownership or SELinux labels reliably).

## 8. Release transaction and artifact acquisition (AD7)

### 8.1 Signed release manifest
One signed document per release lists:
- every service image as an **immutable digest** (`registry/repo@sha256:…`), per **architecture**;
- the network infrastructure artifacts and the bootstrap policy (digests);
- **minimum Manager and runtime versions** (Manager, Podman, helper, kernel features);
- **persistent-state compatibility**: for each store (Gateway database, CredentialsHost vault, ChannelHost database, audit store), the schema versions the release can read and the version it writes, and whether its migration is backward compatible.

At `5ca94f0` the signed manifest (`kautuka-platform-release.json` with `.sig`, `scripts/build-release-assets.sh:593 @5ca94f0`) points at a native tarball and signature (`scripts/kautuka-install-linux.sh.in:2596-2662 @5ca94f0`). Runtime images are allowlisted separately (`src/backend/Kautuka.Manager.RuntimeContainer/Hosting/RuntimeImageAllowlist.cs:98-110 @5ca94f0`, `runtime-images.json`). Revision 4 makes the image digest set part of the signed manifest.

### 8.2 Verification (rev 4.1: the release module is the trust anchor)
- An installed Podman trust policy (`containers-policy.json(5)`, per owner) **enforces signature verification** for Kautuka's registry scopes. The core owner accepts only signed Kautuka images. The workload owner's policy is per scope: signed for Kautuka-built bases, admin-approved digests for third-party connector images (Q32).
- Locally built images (MCPB-materialised connectors, built sandbox images, the local pkgs-proxy wrapper `localhost/kautuka-pkgs-proxy:local`, `src/backend/Kautuka.Manager/sidecars.json:39 @5ca94f0`) cannot carry a release signature. They are built only from verified inputs by Manager, recorded by digest, and are confined to the workload owner (or replaced by release-built images for core sidecars; Q31).
- The release module also verifies the manifest signature and each digest before staging. *Rev 4.1:* Podman's trust policy is a check on the **registry acquisition path only**. It is not relied on for cached or archive-loaded images: with pull policy "never", Podman's image library returns an existing local image without running the registry acquisition path, so no signature policy is evaluated (containers/common `libimage/pull.go`, `PullPolicyNever` handling). `podman load` of an archive does not evaluate registry signature policy either. The trust chain is therefore:

> Verify acquired artifacts and imported archives against the signed release manifest, record the approved immutable image identity, and permit activation only of that verified identity. Test cached, archive-loaded, and locally built images separately.

- "Approved immutable image identity" means the image ID (config digest) and the manifest digest recorded in `release_images` (§12) at verification time. Before every `create`/`run`, Manager checks that the local image's ID equals the recorded one. A local image with the right name but a different ID is refused and reported.
- Locally built images (MCPB-materialised connectors, sandbox images) are recorded the same way at build time, from verified inputs, and are activated only by their recorded ID (§20.14).

### 8.3 Digests, not tags
Containers are always run by digest. Tags are never resolved at run time.

### 8.4 Transaction
1. **Discover** (release metadata through the gateway, §8.5) and **verify** the manifest.
2. **Compatibility check** against the installed Manager and runtime versions and the persistent-state versions.
3. **Stage the full set**: acquire every image and artifact by digest, verify, and store a local archive. **No service is stopped before the full set is staged.**
4. **Activate** through the journal (§8.6).
5. **Assess readiness** with local readiness only (§6.2).
6. **Commit**, or **recover** (§8.7).

- **No independent auto-updates.** No component (Podman auto-update, a sidecar, a connector base) updates on its own. The release module is the only way anything changes version.
- **The last working set is protected from GC**: images, archives and artifacts of the active and the previous committed release are pinned (Manager has no image prune at baseline; any future GC must honour the pin).

### 8.5 Manager and runtime outbound: restricted artifact acquisition
- Manager and both Podman engines reach the network **only through the central gateway**, under a restricted **artifact-fetch policy**: registry API hosts, their auth or token endpoints, blob and CDN redirect targets, signature artifacts, and release metadata hosts. Nothing else.
- **A dedicated fetch worker** (a separate process or container with only the fetch policy, writing into a staging area) is later hardening (Q38).
- **Implicit pulls are disabled.** After explicit acquisition, every `podman run`/`create` uses `--pull=never`. At `5ca94f0`, connector `podman run` sets no pull policy (`src/backend/Kautuka.Manager.RuntimeContainer/Hosting/ConnectorContainerSpecBuilder.cs:11 @5ca94f0`), so a missing image is pulled implicitly. Only builds use `--pull=never` (`src/backend/Kautuka.Manager.RuntimeContainer/Hosting/WorkspaceHostRuntimeAdapter.cs:356 @5ca94f0`, `src/backend/Kautuka.Manager.RuntimeContainer/Hosting/McpbImageMaterializer.cs:261 @5ca94f0`) (§18 Y6).
- **Limit of a transparent gate:** it cannot tell an approved repository from any other use of the same registry host (for example `ghcr.io/devkrity/...` vs `ghcr.io/attacker/...`), because the path is inside TLS. **Digest verification and approved-image selection are therefore local controls** in Manager and in Podman's trust policy, not network controls (§16.4).

### 8.6 Journaled activation
The release module writes an **activation journal** (§12) before each step, with defined power-loss behaviour:

| Step | Journal phase | Power loss here means |
|---|---|---|
| Staged and verified | `staged` | Nothing changed; next boot keeps the current release; staging can resume |
| Maintenance fence on, outbound workers suppressed | `fenced` | Boot with the current release; lift the fence |
| Pre-activation snapshot of persistent state (if the migration is not backward compatible) | `snapshotted` | Boot with the current release; snapshot discarded or kept for audit |
| Old containers stopped, new containers created by digest | `activating` | Boot recovery: start the *current* release from local images (no download), but only after the store inspection below shows every store at its pre-activation schema |
| *Rev 4.1:* migration intent recorded, per store, before any side effect | `migrating` (`store_migrations` rows with `intent`) | Recovery **inspects the actual store state** (schema marker per store, below). Old release only if every store is provably unmigrated; new release (forward) if every store is provably migrated; otherwise **neither image starts**: the state is "unknown or partially migrated" and the release module stops in maintenance for forward completion or an explicit admin-approved restore |
| Migrations run | `migrated` | Forward recovery: start the new release from local images; never restore old data automatically |
| Local readiness passed, still fenced | `verifying` | Same as `migrated` |
| Fence lifted, writes accepted | `committed` | New release is current; any later failure is handled by forward recovery |

- **Migrations are backward compatible, or the release declares a deliberate backup-and-restore or forward-recovery path.** **Old data is never automatically restored after the new version has accepted writes.** At `5ca94f0`, `apply-release` already uses a root-owned journal (`scripts/kautuka-apply-release.sh:23 @5ca94f0`, phases at `scripts/kautuka-apply-release.sh:1407-1430 @5ca94f0`). It suppresses outbound workers until commit and refuses to restore a committed update (`scripts/kautuka-apply-release.sh:1327 @5ca94f0`). That is the right model to carry into the release module. What must still be proven is that no user-acknowledged write happens during its pre-commit verification window, which starts the target release on live data (`scripts/kautuka-apply-release.sh:1412-1422 @5ca94f0`).
- *Rev 4.1:* **migration crash window.** A migration may change data before any completion marker exists, so the absence of `migrated` in the journal does not prove the old release is safe. Required:
  - **durable migration intent before side effects:** a `store_migrations` row per store (`intent`, from/to schema version), fsynced before the migration touches the store;
  - **per-store migration progress or transactional schema markers:** each migration runs in a single store transaction that also writes the schema marker (SQLite `user_version` or a `schema_migrations` row) where the store allows it. Otherwise it records per-step progress in the store itself;
  - **recovery inspects actual store state** (the schema marker and progress in each store), not only the journal;
  - **no old-image start against unknown or partially migrated state:** if any store's marker is not the old version, or progress shows a partial step, the old image is never started;
  - **durable commit/fence ordering before acknowledging application writes:** the journal records `committed` (fsynced) **before** the fence is lifted, and the fence is lifted before any application write can be acknowledged. A crash after `committed` is always forward recovery.
- Readiness for activation is local readiness, never "container started" (§6.2).

### 8.7 Recovery
- Recovery never depends on downloading artifacts. The active and last-working image archives and the network infrastructure artifacts are local (§6.1).
- **Compatible rollback** (previous release reads the current schema): stop new, start previous by digest from local images.
- **Incompatible schema change:** the release module refuses to start the previous image with the new data. It uses the declared path instead: forward recovery, or an explicit admin-approved restore of the pre-activation snapshot that names the data lost.
- Manager, Podman, guest or network infrastructure that cannot start is repaired through the host maintenance path (§14.4).
- Every step is recorded in the audit store and the activation journal.

## 9. Policy model and ownership

### 9.1 Layers
1. **Bootstrap policy** (§14): fixed, small, shipped with the release.
2. **Global endpoint policy** (admin): per component and runtime domain (for example `updateservice → api.github.com:443 dns_bound`; `manager → registry hosts:443`; `channelhost → slack.com, api.telegram.org`), global blocks, special-destination grants (private, link-local, metadata, appliance host).
3. **Connector and skill policy** *(retained, rev2 §7)*: rules attach to the connector or skill.
4. **Narrowing** by users and agents.
5. **Grants** from approvals (§10), each with explicit subject, destination, expiry and scope.

### 9.2 Declaring destinations *(retained)*
- MCPB `manifest.json` allows `_meta` at the root (`src/backend/Kautuka.Gateway/Domain/Connectors/IMcpbPackageService.cs:39-67 @5ca94f0`, validated at `src/backend/Kautuka.Gateway/Domain/Connectors/IMcpbPackageService.cs:154 @5ca94f0`). Declare `_meta["io.kautuka/network"] = { "destinations": [ { "host": "graph.microsoft.com", "ports": [443], "binding": "dns_bound", "why": "Read and send mail" } ], "mode": "ask" }`. Wildcards are a single leading label only.
- Built-in connectors carry the same block in `connector.json`. Mail uses `gmail.googleapis.com:443` (`src/backend/connectors/google-mail/GmailClient.cs:12 @5ca94f0`) and `graph.microsoft.com:443` (`src/backend/connectors/m365-mail/GraphMailClient.cs:11 @5ca94f0`). OAuth token exchange runs in the Gateway service (`src/backend/Kautuka.Gateway/Infrastructure/Agents/McpAgentToolProvider.Proxy.cs:259 @5ca94f0`, `src/backend/Kautuka.Gateway/Infrastructure/Connectors/ConnectorAuthorizationClient.cs:24-36 @5ca94f0`), so the mail container needs one host; the Gateway service needs `login.microsoftonline.com` / `oauth2.googleapis.com` under purpose `mail_oauth`.
- Remote MCP connectors declare their single endpoint implicitly; private endpoints need an explicit `private` grant by an admin (§18 X9).
- Skills declare under skill metadata (format open, Q14).

### 9.3 Evaluation (narrow-only) *(retained, extended)*
For subject `(component | connector C, user, agent?)` and destination `(addr, proto, port, name?, binding)`:
1. Bootstrap or update phase active → only that phase's policy applies.
2. Global block → **deny**.
3. Special destination without a matching special grant → **deny**.
4. Agent block for (agent, C) or (agent, C, destination) → **deny** (only when the agent is reliably known; otherwise agent blocks apply to the whole pod while any blocked agent is active, narrow wins).
5. Owner block on (C, destination) → **deny**.
6. Allowed set = admin-approved subset of declared destinations ∪ persistent rules from "always allow" ∪ unexpired temporary grants.
7. Destination in allowed set **and** the required binding is established → **allow**.
8. Otherwise by mode: `ask` → deny with reason `approval_pending` and raise an approval (§10); `block` → deny; `allow_listed_only` → deny.

Users and agents can only add blocks. Allows come only from the admin at install (system connectors), the owner at install (personal connectors), or an approval answered by the right approver.

### 9.4 Who approves *(retained)*
- System connector: admins (`src/backend/Kautuka.Gateway/Domain/Auth/GatewayOwnershipAccess.cs:37-42 @5ca94f0`). One request per admin, first answer wins, others marked superseded (Q2).
- Personal connector: its owner.
- A user of a system connector cannot widen it; they can block for themselves (Q9).
- Global endpoint policy, special destinations and bootstrap or update policy: admins only.

## 10. Network approvals (asynchronous, design point 8)

- **Ask mode never holds a connection.** The policy service denies promptly (`NF_DROP`, reason `approval_pending`; a prompt reset only through the separately tested mechanism of §5.6.1) and writes a pending-approval event to its store. *Rev 4.1:* pending-approval events come from denied connections **and** from DNS-policy denials (§5.5), which carry a name but no port. Rev2's 60-second hold is removed, and with it the conflict with the 45-second default tool-call deadline (`src/backend/Kautuka.Gateway/Infrastructure/Sandbox/WorkspaceGrpcServiceClient.cs:69 @5ca94f0`, `src/backend/Kautuka.Gateway/Infrastructure/Sandbox/WorkspaceGrpcServiceClient.cs:201-202 @5ca94f0`, `src/backend/Kautuka.Gateway/Infrastructure/Agents/McpAgentToolProvider.Proxy.cs:270 @5ca94f0`).
- The Gateway service reads pending-approval events from the policy service (Unix socket stream; the Gateway service stays the client) and creates a **durable approval request** in `tool_approval_requests` with `kind = 'network'`, `tool_type = 'network_access'`, `mcp_server_id = C`, `arguments_json = {destination, port | null, binding, subject, connector_name, origin: connection | dns_query, first_seen}` (no payload; `port` is null for DNS-originated requests), `run_id`/`session_id` only when reliably known and only for display. Requests are coalesced per (subject, destination, port, approver) while pending.
- Delivery uses the existing paths: desktop Approvals page and API (`src/backend/Kautuka.Gateway/Endpoints/Runtime/GatewayApprovalEndpointMappings.cs:15-234 @5ca94f0`) and channels through `HitlApprovalRequested` with `UserId` = approver (`src/backend/Kautuka.Gateway/Domain/Hitl/HitlEventHandlers.cs:12-65 @5ca94f0`, `src/backend/Kautuka.Gateway/Domain/Channels/ChannelIngressService.ChannelApproval.cs:189 @5ca94f0`).
- Actions (new set in `ApprovalActionCatalog.ForToolType`, `src/backend/Kautuka.Gateway/Domain/Models/GatewayModels.cs:487-520 @5ca94f0`):
  - **Allow temporarily** *(rev 4.1; was "Allow once")* → a **temporary grant**: subject, destination, port (or the declared ports for a DNS-originated request), binding, scope (this pod, or this connector for this user), expiry (proposal 10 minutes, or until the pod ends). Within that window it admits **every** matching connection; it is not a single use. A true "once" would need a defined use budget with atomic consumption in the policy service; it is not offered in the first implementation.
  - **Always allow** → a **persistent rule** added to the connector's allowed set, scoped to the connector (system: all users; personal: the owner).
  - **Block** → a persistent deny rule.
  Temporary grants and persistent rules are separate records (§12) and are shown separately.
- The answer is published as a new policy version and applies to **subsequent attempts**. **A tool call is never automatically replayed.** The agent (or user) retries; the denial reason and approval id are returned to the tool result so the agent can say "waiting for approval to reach example.net".
- **Run plumbing must be bypassed:** `ApprovalResolutionSideEffectApplier` (`src/backend/Kautuka.Gateway/Domain/Hitl/ApprovalResolutionSideEffectApplier.cs:13 @5ca94f0`) and the continuation orchestrator skip `kind = 'network'`; network approvals never pause or resume a run (`src/backend/Kautuka.Gateway/Domain/Execution/AgentChatService.Streaming.Packed.cs:478 @5ca94f0` is not used).
- Expiry: pending network approvals expire after a configurable time (proposal 24 h) through the existing sweeper (`src/backend/Kautuka.Gateway/Domain/Hitl/HitlExpirySweeperService.cs:12 @5ca94f0`); expiry is recorded and has no network effect (the attempt was already denied).
- Requests without a routable approver (no admin paired to a channel) still appear on the desktop (`src/backend/Kautuka.Gateway/Domain/Hitl/HitlEventHandlers.cs:25-29 @5ca94f0` skip rule applies only to channels).
- Every request, answer and expiry is recorded (§11.1).

```mermaid
sequenceDiagram
  participant C as Connector (pod)
  participant P as Policy service
  participant G as Gateway service
  participant O as Approver (desktop / phone)
  C->>P: new flow to new.example:443
  P->>P: mode ask, no rule → deny (RST), record denial
  P-->>G: pending-approval event (stream)
  G->>G: create tool_approval_requests kind=network (durable)
  G->>O: card: Allow temporarily / Always allow / Block
  O->>G: Allow temporarily
  G->>G: create temporary grant (subject, destination, scope, expiry)
  G->>P: publish policy vN+1
  Note over C,P: no replay; the next attempt is evaluated against vN+1
  C->>P: later attempt to new.example:443
  P->>P: grant matches → admit (durable record) → kernel forward
```

## 11. Audit records and Network activity view (design point 6)

### 11.1 Per admitted flow
Each admitted flow has one record with: start time; completion time or last-seen time; completion status (`closed`, `reset`, `timeout`, `revoked`, `unknown`); proven source (component or runtime domain, plus connector or sandbox identity where §5.7 provides it); destination address, port and protocol; hostname and **its source** (`dns_bound` with the lookup id, `sni_bound`, or none); decision, reason and policy version; grant or rule id; bytes in and out; and connector, user, agent, session, run or call **only when reliably available** (with an `attribution` field: `pod`, `call_uid`, `one_of`, `none`).

Limits stated in the record model:
- Rootless Podman translation can hide connector identity from the outer gateway; without a §5.7 mechanism, container rows show only the `work` runtime domain.
- Serialised calls in a reused pod do not prove per-call identity (§5.7.4); such rows use `attribution = one_of`.

Denials: rows where practical, counters under floods (§5.6.4). Approvals: request, answer, answerer, expiry.

### 11.2 Access and retention *(retained)*
- Users see rows whose user is themselves (rows of personal connectors they own, and rows of system connectors attributed to them). Admins see all, including component and bootstrap rows. Mirrors `src/backend/Kautuka.Gateway/Domain/Auth/GatewayOwnershipAccess.cs:67-70 @5ca94f0`.
- Retention: no audit retention exists today (§4.8). Proposal: 90 days of flow rows plus daily roll-ups for 1 year, configurable, defined together for all audit stores (Q16).
- Storage: the policy service owns the flow store (it must write before admitting). The Gateway service reads it through a query API on the policy service's Unix socket and applies ownership filters. Rows are never written by the Gateway service.

### 11.3 Network activity view *(retained)*
A "Network activity" tab on each connector and each agent, plus an admin view for components. Plain sentences, for example: "Microsoft mail connected to graph.microsoft.com 14 times today, sent 2.1 MB, received 18 MB." "Blocked: Microsoft mail tried example.net. Waiting for your approval." "Microsoft mail may reach example.net until 3:40 PM (allowed temporarily)." "Kautuka's update service checked github.com for updates." Hostname wording shows how the name was established ("looked up as", "said it was").

## 13. Failure modes: fail closed (design point 9)

| Failure | Behaviour |
|---|---|
| Policy service not running, crashed, or queue consumer missing | New flows queue without `bypass` and are dropped by the kernel. Admitted flows continue only under still-valid grants in the set (§5.6.5, bounded). |
| Queue full or pending table full | New flows dropped and counted. Never accepted. |
| Audit store unavailable or full | New admissions refused (`audit_unavailable`). |
| Network service restart | Namespaces and nft rulesets persist in the kernel (named namespaces are bind-mounted under `/run/netns`). On start it reconciles to the desired topology; it never deletes a ruleset before the replacement is loaded (atomic `nft -f` transaction). |
| Workload namespace pathname deleted or replaced (for example `ip netns del` by mistake) | *Rev 4.1:* `BindsTo=kautuka-netd.service` does **not** detect this: deleting the bind-mount pathname leaves running processes in the old namespace and does not stop any unit. Defined instead: (1) the network service **reconciles** every 2 s and on netlink and inotify events for `/run/netns`. It compares each expected namespace's pathname, inode and a **namespace generation** (a random id written into the namespace's nft table comment at creation) with its records. (2) On mismatch or absence it marks the namespace generation **retired**: the gateway drops all traffic from the retired generation's veth, and the affected units (Manager or an engine) are stopped through systemd. (3) It recreates the namespace with a new generation, its deny-all table and veth, and only then allows the units to start. (4) Units check at start that the namespace they joined carries the current generation (an `ExecStartPre=` check against the network service), so a unit can never start in a stale or host namespace. `NetworkNamespacePath=` still fails a unit if the path is missing. |
| Manager crash with surviving containers | *Rev 4.1:* containers keep their namespaces inside the core or workload engine's namespace (`kautuka-ns-core` or `kautuka-ns-work`, not `kautuka-ns-manager`), which is still behind the network gateway. Runtime identities stay valid until their expiry or until Manager restarts and re-registers or revokes them. No direct route appears. |
| Stale helpers or namespaces (helpers left running by a killed engine or Manager; *rev 4:* there is no pre-migration case because there are no production installs) | The network service refuses ready while any process of `kautuka-mgr`, `kautuka-core` or `kautuka-work` runs in a namespace other than its current-generation namespace (checked through `/proc/<pid>/ns/net`). The UID backstop drops their traffic meanwhile, and stale helpers are killed before the engine restarts. |
| Update or rollback | *Rev 4:* run only by Manager's release module under the artifact-fetch policy (§8). Recovery uses local artifacts only. A release whose manifest lacks the network infrastructure is refused. |
| IPv6 without IPv6 policy support | Denied at the network gateway; never routed by default. |
| UDP, QUIC, other protocols | Default drop (§5.4.3). |
| Startup before policy is loaded | The network service loads the bootstrap policy (shipped, signed with the release) before any Kautuka unit starts. Until the Gateway service publishes, only the bootstrap and last-activated versions apply. |
| Gateway service down | Published policy continues. `ask` = deny. Approvals queue in the policy service's event store (bounded). |
| Manager cannot register an identity | The pod's traffic has no connector identity and gets only the `work` domain policy, which grants no connector destinations: deny. |
| Uplink down | Flows fail as they would today; DNS returns `SERVFAIL`. |
| *Rev 4:* network infrastructure starts with no application container | Expected. It enforces bootstrap or last-activated policy from its local cache (§6.1). |
| *Rev 4:* core image missing or corrupt at start | Never pulled implicitly (`--pull=never`). The release module loads it from the local archive, or recovers to the last working set (§8.7). |
| *Rev 4:* release staging interrupted | Nothing was stopped; the current release keeps running (§8.4 step 3). |
| *Rev 4:* power loss during activation | Per journal phase (§8.6); no network needed. |
| *Rev 4:* signature or digest verification fails | Release refused; recorded; current release unaffected. Podman's trust policy also refuses at run time. |
| *Rev 4:* one engine (core or work) down | Only that domain stops. The other domain and the network infrastructure continue. Workload start never falls back to the core engine. |
| *Rev 4:* external provider outage (Slack, model provider) | Reported as provider availability; no restart loop, no rollback (§6.2). |

**Removed from revision 2:** monitor-only mode for the Gateway service (rev2 §10 last row, §11), observe-only Phase 0 (rev2 §12), and the rollback flag back to direct non-internal containers (rev2 §12). There is no supported configuration in which a Kautuka flow leaves without the network gateway.

## 14. Bootstrap, install, update and recovery *(rev 4)*

### 14.1 Install
1. The administrator runs the installer, which is already on disk; how it got there is outside the boundary. Because there are no production installs, revision 4 defines a clean install only.
2. The installer package carries the **local last-known-good set**: `kautuka-netd`, the policy service, resolver and audit binaries, the bootstrap policy, Manager, and image archives of the core release. It installs network infrastructure **first** and loads the **bootstrap policy** for the bootstrap identity: release metadata hosts, the signed registries with their auth and blob redirect targets, signature artifacts, and DNS through the central resolver. Nothing else.
3. It creates the two Podman owners (§1.3), each with its own trust policy (§8.2), and loads the core images from the local archives with `podman load`. No pull is needed to reach a running core.
4. Any network step the installer still needs, such as fetching a newer release, runs through the release module's acquisition path under the artifact-fetch policy (§8.5). Today's direct `curl` and `podman pull` steps (`scripts/kautuka-install-linux.sh.in:2600 @5ca94f0`, `scripts/kautuka-install-linux.sh.in:2652 @5ca94f0`, `scripts/kautuka-install-linux.sh.in:2662 @5ca94f0`, `scripts/kautuka-install-linux.sh.in:1704 @5ca94f0`, `scripts/kautuka-install-linux.sh.in:1724 @5ca94f0`) are removed.
5. Bootstrap flows are admitted and recorded like any other. When install completes, the bootstrap identity is disabled.

### 14.2 Updates
- All updates are release transactions run by Manager's release module (§8). UpdateService and `sudo apply-release` are retired (§1.1).
- Network infrastructure updates are part of the signed manifest. They are applied with an atomic ruleset swap, and the old namespaces stay in place. The previous network infrastructure binaries stay in the local last-known-good set.

### 14.3 Boot recovery
- The release module reads the activation journal at Manager start, before it starts any application container, and recovers per §8.6. It needs no network.
- `scripts/kautuka-update-recovery.service @5ca94f0` (`scripts/kautuka-install-linux.sh.in:1130-1148 @5ca94f0`) is replaced. If any recovery step needs the network, it runs after step 2 of §6.1 under the artifact-fetch policy. Otherwise it is offline (`PrivateNetwork=yes`; Q18).

### 14.4 Host maintenance path
- A small, separately versioned root tool that can repair or replace Manager, Podman (both owners' configuration), the guest (WSL distro or, later, the macOS VM) and the network infrastructure. It works when Manager or any container cannot start.
- It uses only local artifacts by default. When it must fetch, it runs in `kautuka-ns-bootstrap` under the bootstrap policy. It has **no general bypass**.
- It is the only supported path for Manager or Podman upgrades that the release module cannot do on itself (Q33).

### 14.5 WSL first boot and maintenance
Monitor-driven setup inside the distro follows §14.1. Windows-side Monitor traffic is outside the boundary (AD2).

## 15. Deployment changes per install type

### 15.1 Linux *(rev 4)*
- Host units: `kautuka-netd.service` (root); policy service, resolver and audit (own UIDs, `CAP_NET_ADMIN` in `kautuka-ns-gw` only); `kautuka-manager.service` (`User=kautuka-mgr`, `NetworkNamespacePath=kautuka-ns-manager`); `kautuka-engine-core.service` and `kautuka-engine-work.service` (`podman system service` as `kautuka-core` and `kautuka-work`, each with `Delegate=yes` and its own `NetworkNamespacePath=`). Whether rootless Podman with the systemd cgroup manager still needs each owner's user manager, and what that means for transient healthcheck units, is part of Gate 1 (Q3, Q4).
- Core services run as containers of the core owner, created by Manager from the active release manifest (by digest, `--pull=never`, hardening per §1.2). The installer no longer writes native system units for the Gateway service, ChannelHost or CredentialsHost, or native user units for WebHost and UpdateService (`scripts/kautuka-install-linux.sh.in:300-301 @5ca94f0`, `scripts/kautuka-install-linux.sh.in:715-740 @5ca94f0`, `scripts/kautuka-install-linux.sh.in:919-948 @5ca94f0`).
- Accounts: `kautuka-mgr`, `kautuka-core`, `kautuka-work`, with non-overlapping `subuid`/`subgid` ranges and separate homes and runtime directories (AD6). The installer verifies that the ranges do not overlap with each other or with any existing entry.
- Socket directories: one per core service on the host, bind-mounted only into the containers that need them (CredentialsHost and Gateway service for the CredentialsHost socket, §1.5). Ownership is expressed in the core owner's mapped IDs (Q36).
- UID backstop in the host namespace: `meta skuid { kautuka-mgr, kautuka-core, kautuka-work }` outbound → drop, with a counter that must stay at zero (AD1 fallback 1, backstop only).
- `kautuka-sandbox` exists only in the workload owner and becomes `--internal` (both creators, `src/backend/Kautuka.Manager.RuntimeContainer/Hosting/WorkspaceHostRuntimeAdapter.cs:519-544 @5ca94f0`, `src/backend/Kautuka.Manager.RuntimeContainer/Hosting/WorkspaceSidecarSupervisor.cs:622-648 @5ca94f0`). Core sidecars get their own network in the core owner.
- Telemetry and the WebHost edge change as in §5.1.3 and §7.1.
- No compose or quadlet exists. If quadlet is chosen to describe core containers, it must be generated from the signed manifest by digest and must not use `AutoUpdate=` (§8.4).

### 15.2 Windows (WSL)
- Same host units and both Podman owners inside the distro; core services as containers. Kernel features to verify on the shipped WSL kernel: named network namespaces, veth, nftables `queue` (`nfnetlink_queue`), conntrack events and deletion by mark, `route_localnet` if used.
- netavark's forced `firewall_driver="iptables"` (`scripts/build-wsl-rootfs.sh:239-253 @5ca94f0`) applies inside the rootless namespace only; the network gateway uses nftables in its own namespace. Coexistence must be tested (both iptables-nft and nft tables loaded).
- Rootless helper: the rootfs installs `slirp4netns` and disables weak dependencies (`scripts/build-wsl-rootfs.sh:149-184 @5ca94f0`); whether `passt` is present is not stated, so the helper in use must be pinned and tested (Q6).
- **The distro's "host" namespace is shared.** The code itself records that a WSL 2 distro does not get its own network namespace: every running distro shares one, so a loopback port is reachable from the user's other distros (`src/shared/Kautuka.Hosting/Hosting/KautukaHostNetworkPolicy.cs:10-14 @5ca94f0`). The uplink, NAT and UID backstop rules that live in that shared namespace are therefore visible to, and modifiable by, root in the user's other distros. The enforcement that matters (default-drop forwarding and admission) must live inside `kautuka-ns-gw`, which other distros cannot enter without access to Kautuka's mount namespace (to verify, Q51). Loopback relays for the WebHost edge (§5.1.3) are reachable from other distros, as today.
- NAT mode only; mirrored refused (`src/installer/Kautuka.Monitor.Core/WslConfigDrift.cs:101-111 @5ca94f0`).
- The Windows host address (WSL NAT gateway) is an `appliance_host` special destination: denied unless granted.

### 15.3 Developer
- Option 1: a developer script creates the same namespaces (needs root once) and runs services inside them.
- Option 2: developer mode is explicitly **unsupported for enforcement** and cannot be shipped. It must not be described as a fallback.
Recommendation: option 1 for CI integration tests; option 2 allowed for inner-loop UI work (Q19).

## 16. Threat model

### 16.1 Assets
Credential vault and mTLS material (core domain only); signed release manifests and the activation journal; connector credentials and OAuth tokens (in connector env, `src/backend/Kautuka.Manager.RuntimeContainer/Hosting/ConnectorContainerSpecBuilder.cs:61-65 @5ca94f0`, and in the Gateway service); mailbox and file contents; agent workspaces; release and update integrity; the policy, grants and audit store; runtime identities.

### 16.2 Adversaries
- A1 Malicious or compromised connector, package or image (including third-party digest-pinned images and MCPB bundles).
- A2 Prompt-injected agent driving a well-behaved connector or the shell.
- A3 Malicious remote MCP server or model provider.
- A4 Local non-admin user trying to widen access.
- A5 Compromised Kautuka service (Gateway service, ChannelHost, WebHost; in rev 4 these are core containers).
- A6 Code that tries to leave by an unhandled route: raw sockets, other protocols, IPv6, a helper outside the boundary, the Windows host.
- *Rev 4:* A7 Attacker who escapes a workload container into the workload owner's account context.
- *Rev 4:* A8 Tampered or substituted release artifact (registry, CDN or mirror compromise; tag move).

### 16.3 What this design stops
- Any Kautuka flow that does not cross the network gateway (G1), including from helpers, pulls, builds, installers and updates.
- Direct access to LAN, private, link-local, metadata and host addresses without an explicit grant (no private bypass).
- Raw-socket, other-protocol, QUIC and unhandled-family escapes (default drop for everything not admitted).
- DNS to resolvers other than the central one; DNS rebinding to private addresses behind public names.
- Unrecorded flows: no admission without a durable record.
- A1/A2 reaching destinations outside their connector's policy (after connector enforcement), and one connector borrowing another's permissions (§5.7.1).
- A4 widening rules (narrow-only, §9.3).
- A5 reaching destinations outside its component policy (for example a compromised ChannelHost cannot reach arbitrary hosts; a compromised CredentialsHost has no network at all).
- *Rev 4:* A7 reaching core storage, credential volumes, core sockets or the core engine (separate owners, disjoint subordinate IDs, no core mounts in workload containers; AD6).
- *Rev 4:* A8 activating an unsigned or substituted image (signed manifest, digests, Podman trust policy, `--pull=never`; AD7).
- *Rev 4:* Recovery that silently discards acknowledged writes (journal, `writes_accepted`, no automatic restore after commit).

### 16.4 What it does not stop (explicit)
1. **Exfiltration through allowed destinations.** No payload inspection.
2. **Shared IPs, CDNs and domain fronting** under `dns_bound`; inner `Host` under `sni_bound`.
3. **ECH**: decisions on the outer name.
4. **DoH to an allowed HTTPS host**: lookups hidden, but connections still need policy.
5. **IP literals** under an IP rule: allowed by design.
6. **Covert channels** (timing, byte counts, DNS query names within allowed suffixes, query strings).
7. **A compromised Manager** can register wrong identities (A or B in §5.7.2) and so mix connector permissions within the `work` domain. *Rev 4.1:* because it controls both engines, its authority is not limited to the union of connector permissions. It also includes the core containers and every path permitted to them (the Gateway service's and ChannelHost's destinations, the core mounts and sockets), as item 13 states. It cannot change the network gateway's rules or the published policy.
8. **A compromised Gateway service** can publish any policy it is allowed to publish (it is the policy manager) and use any Gateway-service source address (§5.7.6). Mitigations: published versions are recorded with the publisher; widening beyond install approvals requires an admin-authenticated action (Q20); global special-destination grants require admin.
9. **Root compromise of the host** or of the network service defeats everything.
10. **Container-to-container traffic** inside a rootless namespace does not cross the network gateway. *Rev 4.1:* it is **not** left open. Lateral connector access is denied by default, and the only permitted shared-service interfaces are enumerated and constrained so they cannot relay (§5.7.7, a Gate 2 requirement). What remains is the residual risk of a flaw in one of those enumerated interfaces.
11. **Traffic outside the boundary**: the host OS, other software on the machine, Windows and the WSL stack (AD2).
12. *Rev 4:* **Host-kernel compromise** from either domain defeats the account split (AD6 limit).
13. *Rev 4:* **A compromised Manager** controls both domains: it orchestrates mounts, images and identities for both (AD6 limit), and holds both engine sockets.
14. *Rev 4:* **Same-host registry content**: the network gateway cannot tell `ghcr.io/devkrity/...` from `ghcr.io/attacker/...`. Only local digest verification and approved-image selection prevent pulling attacker content from an allowed registry host (§8.5). A compromised connector with the registry host allowed in its own policy could still download content from that host. Connector policies should not include registry hosts.
15. *Rev 4:* **Misuse through the authorised Gateway-service link to CredentialsHost** (§1.5).

## 19. Stop gates (replaces revision 3's rollout)

The prototype is four sequential gates. Work stops at the first failed gate. A failure is reported as an architectural result, not worked around downstream. No production installs exist, so there is no in-place migration plan (rev 3 §15.1 is withdrawn). Developer and test machines are reinstalled.

| Gate | What it must establish | Stop condition |
|---|---|---|
| **1. Gated acquisition and closed failures** | A real signed, digest-pinned pull succeeds through the gateway, including authentication and blob redirects. Helpers, DNS, implicit pulls, and stale namespaces cannot bypass it. Gate, admission-worker, audit-storage, queue, and restart failures remain closed. Local recovery artifacts are available. | Any ungated path, unverified activation, or failure that enables unrestricted access. |
| **2. Two connectors, different policies** | Each connector has a trustworthy policy identity before rootless translation obscures it. Concurrent calls, direct IP attempts, alternative DNS, cross-connector impersonation, revocation, and teardown preserve separation. | One connector can use another's permissions, or identity cannot reliably support enforcement. |
| **3. Release transaction and recovery** | Stage and verify a complete release, activate it, assess readiness, and recover from interruption. Demonstrate compatible rollback and explicit handling of incompatible schema changes. | Recovery depends on downloading unavailable artifacts, loses acknowledged state unexpectedly, or starts an incompatible image/data combination. |
| **4. WSL integration and phone access** | The complete layout works on shipped WSL NAT, including startup, restart, helper placement, and the deliberately exposed WebHost path from desktop and phone. | WSL introduces an uncontrolled path or requires an undeclared change to the isolation model. |

**Scope notes per gate**
- **Gate 1** runs on supported Linux with both Podman owners (AD6) and the network infrastructure (§1.1). It does not need every application service migrated. It also includes a **small WSL feasibility smoke check**, limited to the namespace, firewall and packet-admission primitives (named namespaces, veth, nftables `queue` without bypass, conntrack events and deletion by mark), to catch a fundamental platform incompatibility early. The AD1 namespace prototype (Manager and every launch path inside managed namespaces) and the AD4 admission measurements (§21) are part of Gate 1.
- **Gate 2** uses two connectors with different policies. *Rev 4.1:* lateral isolation (§5.7.7) and, for candidate A, authenticated ingress transport are part of what it must establish. Permission borrowing through another connector or through the package service is a stop condition ("one connector can use another's permissions"). The mail connector (approved Microsoft endpoints) and a second connector with a broader policy satisfy the AD3 acceptance test (§20.5). It chooses the identity mechanism of §5.7.2.
- **Gate 3** builds the **minimal core-service socket and health chain** (CredentialsHost → Gateway service → WebHost over sockets, with the §6.2 health signals) because a meaningful application update needs it. The release module (§8) is exercised here.
- **Gate 4** is last: shipped WSL NAT, the full layout, and WebHost reachable from desktop and phone.
- Features downstream of the gates (approvals UI, Network activity views, domain-rule refinements, additional attribution) are built only after the gates they depend on have passed. Additional attribution (milestone 3 in §2.3) remains optional.

### 20.1 Unit
Policy evaluation (every layer, narrow-only, special destinations, bindings), policy version validation, pending-flow table (dedup, bounds, timeouts), DNS answer validation and rebinding, admission record serialisation, approval action mapping, identity registration rules.

### 20.2 Bypass suite (run from every launch path in §4.10, on Linux and WSL)
- TCP and UDP to an internet address and to a LAN address with no rule → denied and recorded.
- IPv6 to a global address and to a link-local neighbour → denied.
- QUIC (UDP 443), SCTP, GRE, raw ICMP echo, raw socket crafted packets (from a test container granted `CAP_NET_RAW` only for the test) → dropped.
- DNS to `8.8.8.8:53`, DoT `:853`, a known DoH endpoint → denied; central resolver answers.
- Metadata `169.254.169.254`, host addresses, the WSL Windows host, `127.0.0.1` of the host namespace → denied.
- Creating interfaces or routes inside a workload namespace (`ip link add`, `ip route add`) → `EPERM`.
- A process started by the user manager (`systemd-run --user curl …`) → no network (or the user manager is not running), counter on the UID backstop shows the attempt.
- `podman build` with a `RUN curl` step and `podman pull` from an unlisted registry → denied and recorded under the `manager` domain.
- *Rev 4.1, split:* (a) **No unadmitted traffic:** kill the policy service, fill the queue, fill the store, stop `kautuka-netd`, delete a workload namespace pathname. Every packet on the uplink capture belongs to a flow that has a durable admission record created **before** the failure, and no new flow is forwarded. (b) **Admitted-flow continuation (separate test):** flows admitted before a policy-service restart continue only while their grant is in the valid set and within the bound (§5.6.5), then stop; revoked grants stop within the revocation bound even during the restart.
- Traffic originating in `kautuka-ns-gw` (resolver upstream, candidate A proxy upstream) is admitted and recorded before transmission; a resolver or proxy socket to any other destination is dropped (§5.6.8).
- Host-namespace capture on the uplink during the whole suite: every packet maps to an admission record.

### 20.3 WSL-specific
Rootless helper placement (each helper process's `/proc/<pid>/ns/net` = `kautuka-ns-core` or `kautuka-ns-work`, per owner; rev 4.1), DNS through the central resolver, IPv6 enabled and disabled in `.wslconfig`, `wsl --shutdown` and restart, distro restart, Kautuka update, attempts to reach the Windows host and to use the WSL DNS tunnelling path, mirrored mode refused.

### 20.4 Policy and DNS
Domain rule with `dns_bound`: allowed after a lookup; *rev 4.1:* denied for an IP literal the source never received from an allowed lookup; **admitted** for a numeric connection to an address the same source did receive (documented as indistinguishable); denied after the binding expires. ECH ClientHello under a strict inner-name rule denied; admitted only with an explicit front-end permission. DNS-policy denial in `ask` mode raises an approval with the name and no port. Shared IP case documented by test. `sni_bound` (candidate A): SNI mismatch denied. Rebinding answer to a private address dropped.

### 20.5 Connector acceptance (AD3)
- Mail connector reaches `graph.microsoft.com:443` (and only its approved Microsoft endpoints).
- Mail connector cannot reach an unapproved destination (`example.net`, a LAN address, the metadata address).
- *Rev 4.1, Gate 2 lateral isolation (§5.7.7):* connector Y cannot reach connector X's listener; Y cannot reach agent sandboxes or core containers other than the enumerated package-service port; Y cannot use the package service to fetch an arbitrary URL, use `CONNECT`, or follow a redirect outside its policy; only the enumerated shared-service interfaces are reachable. Agent-sandbox mode for connectors is refused under enforcement.
- Candidate A: an unauthenticated connection to the identity ingress, or a PROXY v2 header outside the authenticated transport, is rejected; a session authenticated as pod X cannot claim pod Y's identity in its PROXY metadata; records show the connector identity with bytes counted once.
- Mail connector cannot borrow another connector's broader permissions: a second connector with `example.net` allowed runs at the same time for the same user; the mail connector's attempt to `example.net` is denied; repeat with both in agent-sandbox mode (expected: mode refused under enforcement) and after the other connector's pod is recreated (no identity reuse).
- The same for one third-party image connector, one MCPB bundle and one remote MCP connector.

### 20.6 Admission fault injection (AD4)
SYN retransmits and early data during pending (single admission record), pending table full, queue consumer killed mid-burst, policy-service restart with admitted flows (continue until grant bound), store `ENOSPC`, store locked. *Rev 4.1:* deny verdicts are `NF_DROP` and the denied first packet never appears on the uplink (including when a later base chain would accept); the prompt-reset mechanism, if built, is tested separately (RST reaches the client; the packet still never leaves); revocation stops external forwarding within the bound (uplink capture), with endpoint resets checked separately as optional; **revocation during a pending decision** (allow evaluated against generation N, revoke to N+1 before release → dropped, record `revoked_before_release`); **late duplicate verdicts** after revocation follow the rechecked decision; **address and identity reuse** (pod removed, address or identity reassigned) never inherits the old grant or pending decision.

### 20.7 Approvals
Ask → deny promptly → desktop and Slack/Telegram cards → allow temporarily (temporary grant, expiry, multiple connections within the window; DNS-originated request with no port), always (persistent rule), block; system connector routes to admins (first answer wins); personal to owner; no run paused; no tool call replayed; Gateway service down (deny, events queue).

### 20.8 Published AOT binaries
Netlink and nfnetlink interop, trimmed JSON serialisation, cancellation and shutdown, overload, signal handling, run as the target users with only the target capabilities.

### 20.9 Migration, update, rollback
*Rev 4:* superseded by §20.14; in-place upgrade from the `5ca94f0` host layout is not required (no production installs). The rev 3 text follows for reference: upgrade from `5ca94f0` with running persistent connectors and a non-internal `kautuka-sandbox`; update through UpdateService under update policy; refused downgrade; boot recovery after an interrupted update.

### 20.10 Pod lifecycle *(retained from rev2 §13)*
Third-party images based on Alpine, distroless, Debian, scratch, and one with its own non-root `USER`; start-up ordering where PID 1 connects at t=0; forwarder or infra killed mid-call; stdio through `exec -i` and `run --rm -i --pod`; cooldown removes the whole pod; orphan GC after a Manager crash; unique `run --rm` member names; drift on changed forwarder digest or helper options.

### 20.11 Security tests (`src/tests/Kautuka.SecurityTests`)
No identity bytes in upstream captures (candidate A strips the header); no payload in records; non-admin cannot create allows or special grants via the API; a user sees only their own rows.

### 20.12 Runtime-account split (AD6) *(rev 4)*
`subuid`/`subgid` ranges disjoint; separate storage roots, `XDG_RUNTIME_DIR` and engine sockets; no workload container has a core mount, volume, secret or socket (`podman inspect` over all of them); the workload owner cannot read core storage or connect to core sockets (permission tests as `kautuka-work`); Manager rejects a request naming a core image, a host path, `--network host`, `container:` into the other domain, an added capability, or `Exec` against a core container.

### 20.13 Artifact acquisition (Gate 1) *(rev 4)*
A real signed, digest-pinned pull through the gateway, including registry token authentication and blob redirects to the CDN, recorded under the engine's runtime domain. Refused: unsigned image, wrong digest, tag reference, an image from an unapproved repository on an allowed host (local control), implicit pull on `run` (`--pull=never`), pulls from the other owner's engine, helper or DNS paths outside the gateway, and pulls from a stale namespace left by a killed engine.

### 20.14 Release transaction and recovery (Gate 3) *(rev 4)*
Stage a complete release with nothing stopped; tampered manifest refused; power loss injected at every journal phase (§8.6) with the network disconnected; compatible rollback; incompatible schema change: refuse to start old image with new data, and run the declared path; no acknowledged write lost (write, commit, crash, recover, verify); last-working set survives GC; no component updates itself.

*Rev 4.1 additions:* cached, archive-loaded and locally built images are tested **separately**: a local image whose ID differs from the recorded `approved_image_id` is refused for each source; a tampered archive is refused by manifest verification, not by Podman policy. Crash injected after `store_migrations.intent` and before and after each store's transaction: recovery inspects the stores, never starts the old image on a partially migrated or unknown state, and resumes forward or stops in maintenance. Crash between `committed` and fence release, and after fence release: no acknowledged write is lost and no old image starts.

### 20.15 Health model (Gate 3) *(rev 4)*
Liveness vs local readiness vs dependency readiness vs provider availability. Slack and Telegram outage simulated: ChannelHost stays up, no restart loop, no rollback. CredentialsHost readiness over its socket with `--network none`.

### 20.16 Ingress and phone (Gate 4) *(rev 4)*
Only WebHost reachable from the desktop browser and from a phone on the LAN through WSL NAT port forwarding; no other port reachable from LAN, Windows host or other distros; replies do not create outbound permission.
