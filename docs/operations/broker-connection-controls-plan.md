# Broker connection controls implementation plan

Status: independently security-reviewed. The popup handshake below has conditional security approval; its ordering, immutable binding and final session revalidation are mandatory. Kautuka and kautuka-auth change together; backward compatibility is not required. Preserve existing unrelated local changes.

## Reviewed browser-continuity protocol

The Gateway page starts a flow bound to the local cookie/actor and a per-tab random handle kept in sessionStorage, never in a URL. It synchronously opens a broker popup and retains its exact window reference. The popup obtains a bounded, short-lived nonce associated with a host-only Secure HttpOnly broker cookie and the flow. It posts the flow ID and nonce to the opener using the exact Gateway origin. The Gateway page accepts only the configured broker origin, saved popup window, expected message type, flow and nonce format; it posts the nonce and tab handle to its own same-origin Gateway with its original cookie and CSRF checks. Gateway then confirms the recorded nonce/cookie pair using an installation-authenticated broker request. The broker atomically consumes the nonce and immutably binds the flow to that cookie before allowing provider authorization, exchange or completion.

After the fixed provider callback, broker state and the bound cookie are verified along with PKCE, state and provider-specific checks. The popup displays completion and the original page polls its Gateway using the original cookie and tab handle. Gateway revalidates actor, session, origin, intent, cancellation and flow generation before finalization. No provider code, token or final completion credential passes through postMessage; the handshake nonce does. Concurrent flows must not overwrite a shared broker cookie. The supported provider response mode must carry the SameSite=Lax cookie; absent cookie fails closed. Popup blocking or failed opener handshake requires restarting, with no copied-link or manual-code fallback. Opener separation after the initial handshake is allowed.

Security acceptance tests cover copied links in another browser before and after binding, unrelated popups, wrong origin/window/flow, replayed and competing nonce confirmations, concurrent flows, logout/account change/cancel/replacement, missing callback cookies, provider response modes and opener loss. The handshake nonce is a short-lived sensitive binding capability passed through postMessage; exclude it from logs and unrelated telemetry. This protects against copied-link session swaps; it cannot prevent users deliberately authorizing an attacker-controlled installation.

Before release, verify actual browser behavior across two browser contexts and real broker endpoint enforcement, including the fifth/sixth account admission race and refresh racing disconnect. Confirm no legacy initiation, callback, exchange or refresh endpoint bypasses the new controls. Fault-inject a lost provider code-exchange response or crash before persistence: require fresh authorization rather than blindly exchanging the code again. Separately prove that a durably stored result can be retrieved again after a lost response or acknowledgment. Per-location registration limits are approximate abuse controls, not a global installation ceiling.

## Security-review decisions and release criteria

1. **Browser continuity.** Possession of a consent link must not allow another browser to authenticate the initiating Gateway session or attach a mailbox. A broker completion must be proven by the original Gateway browser session, not merely by server-side polling or a broker cookie. Design and review a short-lived flow-bound browser receipt or equivalent before coding this flow. Acceptance test: start in browser A, complete the copied link in browser B, then poll/reload A; A must not become B's identity or gain B's mailbox. Apply to social login, linking and mail.
2. **Supported device experience.** The appliance and browser may be on different machines, but the same browser must start and complete the flow. Switching browsers mid-flow requires restarting. Specify an explicit return/finalization UX that preserves browser continuity without arbitrary broker credential redirects.
3. **Delivery ordering.** Retrieval, authorized browser finalization, durable Gateway persistence and broker acknowledgement are distinct. Persist local success before acknowledgement; permit bounded authenticated idempotent redelivery and do not let acknowledgement loss duplicate grants. Do not deliver provider credentials before verified account identity and atomic admission.
4. **Revocation races.** Disconnect atomically advances connection generation/status. Check generation before provider operations and again before publishing or storing results; stale results after cancellation, suspension or revocation cannot reactivate or be newly delivered. Credentials already released or provider calls already made may remain usable.
5. **Account semantics.** Count distinct verified accounts per provider per installation, separately from individual user/connector credential connections. If the same account is attached to multiple local users, disconnecting one must not release its slot while another remains active. Concurrent admissions are atomic; shared or delegated mailbox access is not automatically counted as separate accounts.
6. **Installation key lifecycle.** Authenticated rotation proves possession of both current and replacement key, preserves stable identity and counts, and atomically retires the old key. A copied key represents the same installation. Unrecoverable key loss creates a new installation and requires reconnection unless a separately designed recovery path is introduced; never recover solely from a claimed ID or provider login.
7. **Unknown provider outcomes.** Distinguish exchange-not-started, in-progress, durable-result and outcome-unknown states. An ambiguous exchange requires a new authorization rather than blind retry; define equivalent recovery when a rotated refresh token response is lost. Do not claim exactly-once behavior across the provider boundary.

## Proposed protocol and boundaries

Use a persistent installation signing key to authenticate broker requests. Keep the existing per-mail-connection DPoP keys: they have separate revocation lifecycles. The installation identity is an allowance and revocation handle, not proof of an official binary.

Gateway creates a broker-owned, short-lived flow bound to the installation, provider, purpose, state, PKCE challenge and (for mail) the connection DPoP key. The browser gets a limited consent capability, completes provider consent through the broker's fixed callback and remains bound to that flow. Gateway retrieves the flow result over authenticated HTTPS; no arbitrary browser return destination is accepted by the broker. Gateway associates completion only with the original authorized mail user or cookie-bound social-login session. A pending, completed, acknowledged, cancelled or expired flow must behave predictably across retries, network loss, concurrent requests and restart.

Broker records count distinct provider-verified accounts, up to five active accounts per provider and installation. Connections are admitted atomically, reconnecting does not use an extra slot, and disconnect prevents future refresh. Provider access tokens already issued may remain valid; connection churn is separately limited. Social sign-in is not charged against mail limits.

Rate limits are independent for installation registration, starts, result retrieval, new mail connections, refresh and failed validation. Initial defaults must permit normal token lifetime and restart behavior, return actionable errors, and be configurable. Operator-facing consent must explain that the destination installation's operator receives the granted mail access.

## Protocol requirements

- Generate a stable installation identity and private signing key using the existing secure storage where appropriate; register its public key automatically with proof of possession. Define concurrent initialization, key rotation, loss and recovery; do not use a bare ID as proof.
- Authenticate installation requests with a short-lived signed proof bound to method, URL, body hash and a fresh replay-protected identifier. Specify audience, proof type, canonicalization, bounded inputs, clock skew and rate limits. Keep the installation signing key separate from per-connection DPoP unless a reviewed lifecycle preserves independent revocation.
- Broker durable flow state binds installation, provider, purpose, state, PKCE challenge, social nonce and mail DPoP key. Provider callbacks use a fixed broker URI and a short-lived signed flow reference. Browser cookies and flow references bind the callback to the initiating flow; neither grants installation polling access.
- Retain social cookie, origin, intent and linking-user checks; retain mail authenticated-user and origin checks. A flow ID alone never claims an operation. Separate-device browsers must complete the same initiating session. Local validation occurs before consuming a result.
- Define idempotent result retrieval, acknowledgement and expiry; exchange the provider code only for the expected flow and verifier. A lost upstream response may leave the provider exchange ambiguous: fail safely and require a new flow rather than claim exactly-once behavior.
- One installation-owned durable record serializes provider/account admissions, revocation and refresh authorization, including concurrent fifth/sixth connections. Obtain a stable provider account identity from a verified identity assertion or documented provider API tied to the actual mail grant; check exact scopes and verification requirements. Do not rely on unverified access-token fields or client-supplied account IDs.
- Broker-mediated refresh must require a currently active installation and connection generation in addition to existing DPoP binding. Disconnect prevents future refresh before freeing a slot, while already issued provider tokens may remain usable. Enforce a configurable rolling new-account connection limit, document its enforcement scope, and measure its effect; reconnecting the same provider account must not count twice.
- Store minimal provider-account information, considering a versioned keyed pseudonym and explicit key rotation, retention and cross-install correlation. Social sign-ins do not count toward mail allowances. Define shared and delegated mailbox semantics.
- Rate-limit registration, flow creation and polling, new accounts, refresh and invalid proofs separately. Inspect existing Cloudflare protections, actual token-refresh patterns and shared-IP effects before choosing defaults. Return 429 with actionable retry behavior; never log secrets, authorization codes or tokens.
- Test wrong-installation access, proof replay, callback/code/state substitution, session swap and social/mail confusion; verify normal and separate-device flows, duplicate callbacks, network failure, recovery and restart. Test verified account identity, cap concurrency, disconnect/reconnect, credential rotation, revocation, refresh and rate-limit behavior. Include real providers and WSL/Linux where feasible; report gaps explicitly.
- Document self-hosted broker configuration and provider approval requirements, service outage and recovery, and the limits of automatic installation identity. Review the final implementation with the software architect and perform security review where warranted.

## Work and validation

### Implemented locally

- The broker owns short-lived authorization flows, binds the browser to the initiating Gateway session, uses a fixed provider callback, and returns results to the installation through signed polling. PKCE, state and per-mail-connection DPoP remain in use. A provider exchange with an unknown outcome is terminal; only a durably recorded result can be retrieved again.
- Gateway and frontend use the bound social and mail flows. CredentialsHost stores encrypted, atomic mail activation and refresh state. Cancellation, disconnect and recovery check the exact flow and generation; failed disconnects block local use until removal is retried. Retired hosted-protocol routes are blocked before their handlers.
- Provider-verified, installation-scoped mailbox identities enforce five distinct active Google accounts and five Microsoft accounts per installation. A configurable rolling new-account budget survives disconnect; limit denials are terminal and user-facing. The pseudonym key must be backed up with broker state; changing it without migration breaks accounting.
- Installation identities are scoped to the broker origin. Rotation signs the replacement key with both old and new keys, preserves the installation ID and quotas, and recovers a lost response from durably staged local keys. A loopback, administrator-authorized maintenance endpoint initiates rotation. Intermediate unscoped feature-branch identities are deliberately not migrated.
- Settings → Advanced → Authentication queues a broker origin and separate social sign-in client IDs for the next restart. A switch is fenced against in-flight mail work and key rotation and rejected while mail state remains. Credentials are bound to their issuing origin. An active password-bearing administrator is required when the change is queued; subsequent account changes can still remove that recovery path.
- Separate approximate per-IP, per-Cloudflare-location budgets protect registration, starts, polling, control, refresh and invalid proofs. Malformed signed bodies remain covered by the coarse request budget. Shared networks may encounter these limits together.
- This is a coordinated breaking change. The user permits users to sign in and reconnect their mail rather than requiring migration of the old protocol. Provider access-token lifetime and sender binding are not assumed.
- Obsolete hosted mail credentials are reported as requiring reconnection and removed on explicit disconnect or successful replacement. Existing authenticated Gateway sessions are not automatically invalidated by retiring broker endpoints; pending login flows do not survive a restart.
